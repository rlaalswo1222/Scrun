실시간 같이 뛰기: 어떤 방식으로 주고받을까

결정(11/10 민재): A. FastAPI WebSocket → docs/adr/0010-realtime-websocket.md

1. 무엇을 주고받나

같은 코스(= 맵 하나, 최대 20명)에 들어온 사람들의 폰이 서로의 상태를 계속 알아야 합니다. 백로그 BL-21(공동 맵)·BL-23(페이스 봇)·BL-25(스파이크)에서 필요한 것만 뽑으면:

폰 → 모두: 나는 코스 시작점에서 1240.5 m, 지금 9.8 km/h (+ 닉네임·인증 마크는 입장 때 한 번)
서버 → 모두: 누가 들어왔다 / 나갔다, 봇은 몇 시에 출발해서 몇 km/h로 달린다
얼마나 자주: 1초에 1–2번 (기획 흐름도 v2 "실시간 러너는 위치를 1초에 1–2번 주고받음")

여기서 중요한 사실 세 가지:

  • 위치가 1차원입니다. 코스 위 거리(m) 숫자 하나. 총 게임처럼 방향·충돌·물리가 없습니다.
  • 속도 추정 자체가 이미 늦습니다. 러닝머신 속도를 바꾼 뒤 우리 추정이 따라오기까지 예비 실험 평균 약 5–6초(BL-13 열린 질문 Q-11). 네트워크가 0.2초 늦는 건 그에 비하면 작습니다.
  • 양이 아주 적습니다 계산. 한 사람 상태가 JSON 약 80바이트라면, 20명 × 1초 2번 × 80B = 폰 한 대가 받는 양 초당 약 3.2KB. 사진 한 장보다 훨씬 작습니다.

그래서 다른 사람 아바타는 "받은 위치를 그대로" 그리지 않고, 마지막으로 받은 위치 + 그 사람 속도 × 지난 시간으로 계속 앞으로 움직이다가 새 값이 오면 부드럽게 맞춥니다(보간). 러닝머신 속도는 천천히 바뀌어서 이 방식이 잘 맞습니다. 어느 방식을 고르든 앱 쪽은 이렇게 그립니다.

2. 두 방식 그림으로

비유 — A는 우리 가게에 전화선을 직접 까는 것입니다. 손님(폰)이 이미 우리 가게(서버)에 회원증(로그인 토큰)을 보여 주고 들어오니, 같은 문으로 대화방까지 들어오게 합니다. 대신 전화 교환 일은 우리가 합니다.
B는 전화 교환 회사(Photon)를 빌리는 것입니다. 교환·인원 제한·끊김 처리는 회사가 해 주고 서울에 지점도 있습니다. 대신 손님 명단(누가 몇 명 들어와 있는지)이 회사에 있어서, 우리 가게가 그걸 알려면 따로 물어봐야 합니다.

3. 항목별 비교

초록 칸이 우리 앱에 더 유리한 쪽입니다.

A. FastAPI WebSocketB. Photon Fusion 2 (공유 모드)
서버 코드우리가 씀: 방 입장·퇴장, 받은 상태를 같은 방에 다시 보내기, 20명 제한, 봇 정보. FastAPI 공식 문서에 같은 모양의 예제가 있음안 씀. 방·중계는 Photon이 함

로그인지금 accessToken 그대로. 만료 처리도 ApiClient와 같은 규칙Photon "커스텀 인증" 설정: Photon이 우리 서버 주소로 토큰을 보내 확인받음. 우리 서버에 확인용 API 하나 추가
20명 · 입장 잠금입장 API와 같은 서버가 셈 → 숫자가 항상 맞음Photon 방 최대 인원으로 막을 수 있음. 다만 입장 API(우리 서버)의 인원과 Photon 방 인원이 따로 놀아서 둘을 맞춰야 함
지금 달리는 사람 수서버에 붙어 있는 연결 수 그대로 (지환 질문 1 해결: 샘플 주기와 상관없어짐)우리 서버는 Photon 방 인원을 바로 모름 → 지금 임시 방식(기록 + updated_at) 유지
봇 (BL-23: 모두에게 똑같이, 수·페이스는 서버 설정)서버가 "출발 시각·페이스"를 내려 주고 각 폰이 위치를 계산 → 모두 같은 위치방장(방을 만든 폰)이 봇을 맡는 게 기본. 방장이 나가면 다른 폰으로 자동으로 넘어감. A처럼 서버 설정값을 받아 계산하게 할 수도 있음
지연오라클 싱가포르. 이 노트북에서 실측 중앙값 약 0.22초 (아래 4절)서울 지역(kr) 있음. 실측은 안 함 — 같은 시각 서울 AWS가 0.04초라 그 근처일 것 가설
끊겼다 다시 붙기 (BL-25 ⑤)직접 짬: 다시 연결 → 방 상태 다시 받기. 헬스장 와이파이 70초 끊김(10/29 실측)도 이 처리로Fusion의 재접속 지원 범위는 이번에 확인 안 함. 어느 쪽이든 70초 끊김은 앱이 따로 처리해야 함
비용 (출시 뒤)지금 쓰는 오라클 무료 서버 안에서. 위 계산대로 양이 작아 2코어·11GiB면 여유 가설무료 100 CCU(동시 접속 100명, 출시 가능, 앱 1개). 넘으면 500 CCU 월 $125. 개발용 무료 20 CCU는 출시 불가
우리가 지킬 것서버가 꺼지면 같이 뛰기도 멈춤. 서버 한 프로세스 안에 방이 있어서, 나중에 서버를 여러 대로 늘리면 Redis 같은 공유 저장소가 필요중계 서버 운영은 Photon 몫. 우리는 대시보드·앱 ID 관리
11/13 시연까지이미 아는 것(FastAPI·JSON·우리 인증)만 씀Fusion을 처음 익혀야 함 + 우리 서버와 두 군데를 맞춰야 함

4. 지연 실측 (11/10, 이 Windows 노트북 와이파이)

"서버까지 갔다 오는 데 걸리는 시간"을 보려고 TCP 연결 시간(왕복 한 번)을 12–15번 쟀습니다. 실측

AWS 서울 (비교용)39 ms22357
AWS 싱가포르 (비교용)96 ms781698
오라클 싱가포르 (우리 서버)222 ms107318
  • 같은 싱가포르인데 오라클이 AWS보다 2배 넘게 깁니다. 오라클까지 가는 길(통신사 경로) 문제로 보입니다 가설. 최대값이 튀는 건 노트북 와이파이 탓일 수 있습니다.
  • 화면에서는 얼마나 차이 날까 계산: 10 km/h는 초당 2.8 m. 0.22초 늦으면 다른 사람 아바타가 약 0.6 m 뒤에 그려집니다. 1절의 보간을 쓰면 이 차이는 "조금 늦게 따라오는 것"으로만 보입니다.
  • 아직 모르는 것: 아이폰 LTE·헬스장 와이파이에서의 값, 실제 WebSocket 메시지 왕복. S3에서 기기 2대로 잽니다.

5. 추천과 위험

추천: A. FastAPI WebSocket 제안
① 우리가 주고받는 건 숫자 두 개(거리·속도)를 1초에 1–2번이라 Photon Fusion 같은 게임 엔진급 도구의 장점(틱·예측·물리)을 쓸 데가 없습니다.
② 서버가 정해야 하는 규칙(20명, 입장 잠금, 봇, 지금 달리는 사람 수)이 이미 우리 서버에 있습니다. A면 한 곳에서 다 정하고, B면 우리 서버와 Photon 두 곳을 맞춰야 합니다.
③ 로그인 토큰과 오류 규칙을 그대로 씁니다. 앱도 ApiClient 옆에 비슷한 크기의 코드 하나가 붙는 정도입니다.
④ 출시 뒤 동시 접속 100명을 넘어도 서버비가 갑자기 생기지 않습니다.
A의 위험과 대응
• 싱가포르 지연(약 0.22초): 보간으로 가립니다. S3에서 아이폰으로 실측해 화면에서 문제가 보이면 서버를 서울·춘천으로 옮기는 걸 운영 서버 작업(BL-51)에 넣습니다.
• 끊김·재접속을 직접 짜야 함: S3에는 "다시 붙으면 방 상태 다시 받기"까지만, 오래 끊긴 경우는 S4 측정 예외(BL-15)와 같이 처리합니다.
• 서버 한 대·한 프로세스: 지금 서버는 uvicorn 하나로 떠 있어 방을 메모리에 둬도 됩니다. 사람이 많아져 서버를 여러 대로 늘릴 때 Redis를 붙입니다(그전엔 안 함).
• 나중에 바꿀 길: 앱에서는 화면 코드가 "같이 뛰기 연결" 인터페이스만 보게 만들어, 나중에 Photon으로 바꿔도 화면은 그대로 둡니다.

B를 고를 만한 경우: 지연이 실제로 화면에서 문제가 되는데 서버를 옮기기 어려울 때, 또는 나중에 같이 뛰기에 몸싸움·실시간 경쟁처럼 게임다운 동작이 많이 붙을 때입니다. 그때는 이 표를 다시 보고 바꿉니다.

A로 정하면 바로 할 일

  1. ADR 작성(번호는 맥에서 쓰는 브리지 ADR-0009 다음).
  2. 메시지 정하기: join(입장 정보) · state(거리·속도) · roster(들어옴·나감) · bots(봇 출발 시각·페이스). 입장 API 응답의 realtime.url·token 모양을 확정하고, docs/api/README.md의 "지금 달리는 사람 수"를 "실시간 연결 수"로 바꿉니다.
  3. S3: 서버 /v1/rt + 앱 연결 코드 + 기기 2대로 지연 실측(BL-25 ①⑤⑥).
  4. 지환님께 알림: 샘플 주기와 runs.updated_at 문제는 더 신경 쓰지 않아도 됩니다.

6. 안 고른 후보 · 공부 자료

  • Photon PUN 2 · Photon Realtime: 같은 회사의 옛 방식/저수준 방식. 출시 가능한 무료 100 CCU는 Fusion·Quantum에만 해당해서 비교 대상을 Fusion으로 잡았습니다.
  • Unity Netcode + Unity Relay, Colyseus, Nakama: 게임용 넷코드이거나 서버를 하나 더 두는 방식이라 B와 같은 이유(우리에겐 과함, 규칙이 두 곳)로 깊게 보지 않았습니다. 가격도 이번에 확인하지 않았습니다.

공부 자료

  • MDN — WebSocket API: WebSocket이 무엇인지(연결 한 번 열어 두고 양쪽이 아무 때나 보냄)
  • FastAPI — WebSockets: "Handling disconnections and multiple clients"의 ConnectionManager가 A 서버의 뼈대와 같은 모양
  • NativeWebSocket: Unity용 WebSocket 라이브러리(iOS 지원, Apache 2.0). A의 앱 쪽 후보
  • Gabriel Gambetta — Entity Interpolation: 다른 사람을 "조금 과거"로 부드럽게 그리는 방법(1절 보간)
  • Photon Fusion — Network Topologies: 공유 모드(각 폰이 자기 것을 책임) 설명
  • Photon Fusion — Shared Mode Master Client: 방장이 나가면 자동으로 넘어가는 규칙
  • Photon Fusion 가격 · 요금제 설명 (무료 20 CCU는 개발용, 무료 100 CCU는 출시 가능·앱 1개)
  • Photon 지역 목록 (서울 kr) · 커스텀 인증
  • Caddy reverse_proxy: 지금 서버 앞단(Caddy)이 WebSocket을 설정 없이 통과시킴 → A는 서버 설정을 안 바꿔도 됨

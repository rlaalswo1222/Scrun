# ADR-0001: 앱 전체를 Unity 하나로 만든다

- 상태: 승인 (소급 기록)
- 날짜: 2026-10-15 (3D 화면), 2026-10-26 (앱 전체), 2026-11-06 (네이티브 앱 + Unity 안 비교 보충)
- 결정한 사람: 팀 (멘토 피드백 반영)

## 배경
달리는 화면은 3D 코스와 아바타가 필요하고, 로그인·친구·기록 같은 일반 화면도 필요하다. 처음 프로토타입은 Three.js(웹)로 만들었다(`run3d/`, `maptest/`).

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| Three.js를 앱 웹뷰에 넣기 | 프로토타입 재사용, 웹 기술 | 폰 웹뷰에서 3D가 느림(멘토 지적), 센서 접근 제한(브라우저 가속도 60Hz) |
| Flutter(일반 화면) + Unity(3D) 섞기 | 일반 화면 만들기 편함 | 두 엔진 연동·빌드·상태 공유가 복잡, 팀이 둘 다 처음 |
| SwiftUI 네이티브 앱 안에 Unity 넣기(Unity as a Library, 11/06 보충) | 일반 화면이 SwiftUI라 쉬움, 카카오·Apple 로그인 SDK를 그대로 씀 | Flutter + Unity와 같은 구조: Xcode·Unity 두 프로젝트를 합쳐 빌드, 화면 사이 상태(로그인·방·고스트·보정값)를 넘기는 다리 필요, Unity 버전 올릴 때 연결이 깨질 수 있음. Unity 런타임은 통째로 올라가서 앱 크기·메모리 이득이 작고 달리기 화면 진입 때 대기 생김. Swift 아는 사람 1명. 안드로이드로 갈 때 껍데기를 다시 만들어야 함 |
| Unity 하나로 전부 | 한 언어(C#)·한 빌드, 3D 성능, 네이티브 센서 플러그인 | 로그인·목록 같은 일반 UI가 Flutter보다 불편, 앱 크기 큼 |

## 결정
Unity 6(URP)로 앱 전체를 만든다. 센서는 네이티브 플러그인(안드로이드 Java/Kotlin, iOS Swift — 에어팟 CMHeadphoneMotionManager).

## 이유
- 핵심 화면(달리기)이 3D이고 폰 성능이 중요함. S22에서 섬 월드 30fps 확인
- 팀 3명 모두 Unity·Flutter 경험이 없어서, 배울 것을 하나로 줄이는 게 유리
- 고속 센서가 필요함: 웹은 가속도 60Hz 제한, 네이티브는 S22에서 420Hz (10/28 SpeedLab)
- (11/06 보충) 아이폰 전용이 된 뒤(ADR-0007)에도 유지: 앱의 중심이 3D(달리기·방 대기·함께 달리기·고스트)라 네이티브 껍데기가 맡을 화면은 로그인·목록 정도뿐이고, 그 이득보다 두 프로젝트 연동 비용이 큼. 센서·속도 계산은 이미 Swift 플러그인이라 네이티브가 꼭 필요한 곳에만 네이티브를 씀. Figma 94개 화면의 오토 레이아웃이 UI Toolkit으로 거의 그대로 옮겨짐(11/05 확인)

## 결과와 위험
- 일반 화면은 Unity UI Toolkit으로 만들어야 함 → 화면 흐름 작업 때 학습 필요
- APK가 큼(본 앱 85MB). 플레이 기본 모듈 제한 200MB 안
- 카카오·Apple 로그인은 네이티브 SDK라 Unity 플러그인으로 감싸는 작업이 따로 듦
- 다시 검토할 조건: UI Toolkit으로 로그인·친구 화면을 만드는 비용이 예상보다 훨씬 클 때

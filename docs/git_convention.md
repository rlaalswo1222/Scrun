# Git 규칙 (브랜치·커밋 메시지)

팀원 모두(그리고 Claude)가 지킨다. 저장소를 처음 받으면 아래 "검사기 켜기"를 한 번 실행해 두면, 규칙에 안 맞는 커밋은 막힌다.

## 브랜치
| 브랜치 | 역할 |
|---|---|
| `main` | 발표·출시한 상태만. 직접 커밋하지 않는다 |
| `develop` | 개발 중 합쳐지는 곳. 직접 커밋하지 않는다 |
| `feat/이름` 등 | 작업 하나당 하나. `develop`에서 따서 `develop`으로 PR |

- 작업 시작: `git switch develop` → `git pull` → `git switch -c feat/짧은-이름`
- 브랜치 이름은 `유형(소문자)/영어-소문자-하이픈`. 예: `feat/google-login`, `fix/speedlab-segment-count`, `docs/wireframe-v1`
- 끝나면 브랜치를 올리고(`git push -u origin feat/...`) GitHub에서 **`develop`으로** PR. 합친 뒤 브랜치는 지운다
- 발표·출시 때만 `develop` → `main` PR로 합친다

## 커밋 메시지 모양
```
유형: 제목

- 무엇을 바꿨는지
- 왜 바꿨는지
```
- 첫 줄: `유형: 제목`. 유형 뒤에 콜론과 공백 한 칸
- 제목과 본문 사이는 **빈 줄 하나**
- 제목·본문은 **한글**. 본문은 "어떻게"보다 **무엇을, 왜** 바꿨는지
- 항목이 여러 개면 글머리 기호(`- `)
- 제목은 **50자 이내**, 끝에 마침표(`.`) 금지

## 유형
| 유형 | 언제 |
|---|---|
| `Feat` | 새 기능 추가 |
| `Fix` | 버그 수정 |
| `Docs` | 문서 수정 |
| `Style` | 코드 모양만(줄 맞춤, 세미콜론 등), 동작 변화 없음 |
| `Refactor` | 동작은 같고 코드 구조만 개선 |
| `Test` | 테스트 코드 추가·수정 |
| `Chore` | 빌드·패키지·설정 등 기타 (예: `.gitignore`) |
| `Design` | UI 디자인 변경 (CSS, 화면 배치 등) |
| `Comment` | 주석만 추가·변경 |
| `Rename` | 파일·폴더 이름 변경이나 이동만 |
| `Remove` | 파일 삭제만 |
| `!BREAKING CHANGE` | 큰 API 변경 (다른 코드가 깨질 수 있음) |
| `!HOTFIX` | 급하게 고쳐야 하는 치명적 버그 |

유형은 표에 적힌 그대로 쓴다(첫 글자 대문자).

## 한 커밋에는 한 가지 문제만
- 나중에 "언제 무엇 때문에 바뀌었나"를 추적할 수 있게
- 기능 추가와 버그 수정, 문서 수정이 섞이면 커밋을 나눈다

## 예
좋은 예
```
Feat: SpeedLab 실시간 속도에 걸음 수 추가

- 속도 = a + b·ln(충격) + c·spm, 달리기 보정 4구간 이상일 때만
- est.csv에 충격만·충격+걸음 수 값을 둘 다 기록
- 10/28 기록 재계산에서 충격만보다 평균 오차가 작아서 (계획 0005)
```
```
Fix: 안내 검증 끝 기록의 구간 수가 하나 많던 문제

- 모드를 끝낸 뒤에 구간 수를 읽어서 보정 모드 값(7)이 기록됨
- 끝내기 전에 구간 수를 저장하도록 바꿈
```
나쁜 예
```
수정함.            ← 유형 없음, 무엇을 고쳤는지 모름, 마침표
feat: 이것저것      ← 유형 소문자, 여러 문제가 한 커밋에
```

## 검사기 켜기 (저장소마다 한 번)
```
git config core.hooksPath tools/githooks
```
이후 `git commit` 때 `tools/githooks/commit-msg`가 첫 줄(유형·콜론·50자·마침표)과 빈 줄을 검사한다. 병합(Merge)·되돌리기(Revert) 자동 메시지는 통과시킨다.

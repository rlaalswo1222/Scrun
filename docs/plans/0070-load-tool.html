부하 테스트 도구 고르기

계획 0070 정할 것 2 → ADR-0014. 2026-11-25 민재. 서버(FastAPI + PostgreSQL + WebSocket)에 가짜 사용자를 수백 명 붙여 "어디가 얼마나 느린지"를 재는 도구를 고른다.

한 줄 요약
오픈소스 부하 도구에서 많이 쓰이는 건 JMeter·Gatling·k6·Locust 넷이다(k6·Locust 둘만이 아님). 다만 우리 조건(파이썬 서버, 스크립트를 git으로 리뷰, WebSocket 시나리오, 작은 ARM VM)에선 JMeter·Gatling이 먼저 빠지고 k6 vs Locust가 남는다. 추천은 k6: WebSocket이 내장이고, "p95가 300 ms 넘으면 실패" 같은 판정이 한 줄이며(계획의 "같은 시험 3번, p95 차이 10% 안" 판정에 바로 씀), 작은 VM에서도 부하를 많이 만든다. Locust를 고르면 파이썬이라 익숙하지만, WebSocket·판정을 직접 짜야 한다.

업계 자료

  • 도구 비교 글들은 대개 JMeter·Gatling·k6·Locust를 "오픈소스 4강"으로 묶는다. JMeter는 1998년부터 기본 선택지였다고 Gatling(경쟁사) 글도 적는다. 다만 대부분 도구 만든 회사나 블로그 자료라 사용량 측정이 아니다.
  • ThoughtWorks Technology Radar는 k6를 2020-10 Assess → 2021-04 Trial → 2022-10 Adopt로 올렸다(개발자 경험·CI 연결을 이유로). Locust·Gatling이 Radar에 오른 기록은 이번 검색에선 못 찾았다.

결론: "가장 많이 쓰이는 둘"이라기보다 4강 가운데, 코드로 시나리오를 쓰는 요즘 방식의 대표 둘이다. wrk·Vegeta·hey는 별은 많지만 "로그인 → 홈 → 기록 목록" 같은 흐름을 못 그려서 우리 S1–S4엔 안 맞는다(엔드포인트 하나 미세 측정할 때 보조로는 쓸 수 있음).

JMeterGatling

3. k6 vs Locust — 우리 시나리오에 대 보기

기준k6Locust
시나리오 언어JavaScript(TypeScript도). Node.js가 아니라 npm 패키지는 그대로 못 씀Python. 서버·speedlab과 같은 언어
S1 앱 켜기·S2 달리기(HTTP)쉬움쉬움
S3 실시간 20명 WebSocketWebSocket 모듈 내장내장 없음. WebSocket 클라이언트로 User 클래스를 직접 짜거나 locust-plugins. 연결별 지연을 Locust 통계에 넣는 것도 직접
S4 계기판 사진 3장 업로드multipart 내장(http.file)requests 방식 files=
판정(문턱)thresholds: { http_req_duration: ['p(95)<300'] } 한 줄, 넘으면 종료 코드 실패 → CI에 그대로내장 없음. 이벤트 훅에서 종료 코드를 직접 정하거나 locust-plugins
결과끝에 요약(p90·p95, p99는 설정으로 추가), JSON·CSV, Prometheus로 보내기 내장실시간 웹 화면(그래프)이 보기 좋음. --headless --csv로 백분위 CSV
부하 만드는 힘Go라 한 프로세스가 CPU 코어를 다 씀. 작은 VM에서도 수천 가상 사용자파이썬 프로세스 하나 = 코어 하나. 늘리려면 --processes나 master·worker 여러 개
설치바이너리 하나(Linux ARM64 있음)pip install locust
fake_runner.py 재사용로그인·입장 순서만 옮겨 적음로그인 함수는 거의 그대로. 실시간 부분은 asyncio라 Locust(gevent)에 그대로 못 넣어 다시 써야 함 — 계획 0070에 "재사용 쉬움"이라 적은 건 반만 맞음
라이선스AGPL-3.0 (우리 서버에 넣는 게 아니라 시험할 때만 돌려서 공개 의무와 무관)MIT
취업·면접 설명"k6로 p95 문턱을 걸고 CI에서 돌림" — 요즘 백엔드 공고·글에서 흔함"Locust로 파이썬 시나리오" — 파이썬 팀에선 흔함

같은 S1을 두 도구로 (모양만 보여 주는 예시, 아직 돌려 보지 않음)

k6 s1_open_app.js 
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  stages: [{ duration: '1m', target: 50 },
           { duration: '5m', target: 50 }],
  thresholds: {
    http_req_duration: ['p(95)<300'],
    http_req_failed: ['rate<0.01'],
  },
};
const BASE = __ENV.BASE;
let auth;  // 가상 사용자마다 따로

export default function () {
  if (!auth) {
    const r = http.post(`${BASE}/v1/auth/kakao`,
      JSON.stringify({ kakaoAccessToken: `k_${__VU}` }),
      { headers: { 'Content-Type': 'application/json' } });
    auth = { headers: { Authorization:
      'Bearer ' + r.json('success.data.accessToken') } };
  }
  for (const p of ['/v1/home', '/v1/friends', '/v1/feed'])
    check(http.get(BASE + p, auth),
          { '200': (r) => r.status === 200 });
}
실행: k6 run -e BASE=http://시험서버 s1_open_app.js
Locust s1_open_app.py 
import itertools
from locust import HttpUser, task, between

ids = itertools.count(1)

class AppUser(HttpUser):
    wait_time = between(1, 3)

    def on_start(self):
        r = self.client.post("/v1/auth/kakao",
            json={"kakaoAccessToken": f"k_{next(ids)}"})
        token = r.json()["success"]["data"]["accessToken"]
        self.client.headers["Authorization"] = \
            f"Bearer {token}"

    @task
    def open_app(self):
        for p in ("/v1/home", "/v1/friends", "/v1/feed"):
            self.client.get(p)

# 문턱(p95 < 300 ms) 판정은 따로 이벤트 훅으로 짜야 함
실행: locust -f s1_open_app.py --headless -u 50 -r 1 -t 6m --csv out --host http://시험서버

가짜 계정 k_숫자는 시험 서버의 KAKAO_MODE=fake에서만 됨. 가입이 안 된 계정은 가짜 데이터 넣기(seed_load.py)에서 미리 만들어 둔다.

4. 나머지 정할 것 3개 (계획 0070)

1. 어디서 돌리나 — 추천: 오라클 무료 ARM VM 하나 더(운영과 같은 2코어 ARM)
새로 본 것: 부하를 만드는 쪽도 어딘가에 있어야 한다. 같은 VM에서 돌리면 서버와 CPU를 나눠 써서 수치가 틀어진다. 무료 ARM 한도(오라클 문서 기준 합계 4코어·24 GB, 우리 계정에서 확인 필요)를 운영 2 + 시험 서버 2로 다 쓰면, 부하는 노트북에서(한국 → 싱가포르, 실제 사용자와 같은 길) 걸고 서버 안의 순수 처리 시간은 지연 로그 미들웨어로 따로 본다. k6처럼 가벼운 도구일수록 노트북·작은 VM에서도 충분하다.
3. 관측 범위 — 추천: 최소(요청마다 지연 로그 + pg_stat_statements + 도구 요약 + docker stats)
Prometheus·Grafana는 대시보드가 보기 좋지만 시험 VM 메모리와 설정이 늘어난다. 기준선을 먼저 뽑고, 발표·면접용 그림이 필요하면 그때 붙인다(k6는 Prometheus로 보내기가 내장이라 나중에 붙이기 쉬움).
4. 가짜 데이터 크기 — 추천: 계획 그대로 사용자 1만 · 기록 100만까지 단계로(1천 → 1만 → 10만 → 100만)
지금 운영 DB(사용자 2명·기록 20개)로는 인덱스 차이가 안 보인다. 어느 단계에서 피드·목록이 꺾이는지가 다음 계획(인덱스·EXPLAIN)의 근거가 된다. 크기는 가정한 시험값이고 실제 사용자 수 예측이 아니다.

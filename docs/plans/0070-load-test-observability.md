# 계획 0070: 부하 테스트·관측 기반 — 서버 성능을 수치로 말하기

- 상태: **계획**(2026-11-25 민재 요청, 승인 전)
- 담당: 민재
- 왜: 서버 개선(OCR 비동기 큐, 피드·목록 인덱스, 실시간 Redis 확장)을 하려면 "어디가 얼마나 느린지"를 먼저 재야 함. 지금은 잴 길이 없음. 11/25 기록·친구 로딩 원인을 볼 때도 서버에 SSH로 들어가 손으로 쟀음. 운영 DB는 사용자 2명·기록 20개라 API 처리가 5–18 ms라서, 부하와 대량 데이터 없이는 개선 전후가 안 보임
- 이 계획의 결과물: **다시 돌릴 수 있는 부하 시나리오 + 대량 가짜 데이터 + 서버 지표 + 첫 기준선 표**. 개선은 하지 않음(다음 계획들이 이 기준선과 비교)

## 정할 것
1. **어디서 돌리나**
   - (가) **오라클 무료 ARM VM을 하나 더**(추천): 운영과 같은 2코어 ARM이라 수치를 그대로 옮길 수 있음. 지금 서버가 2코어·12 GB를 쓰고 있어 무료 한도(Ampere A1 합계 4코어·24 GB, 확인 필요) 안
   - (나) 노트북 Docker: 공짜·빠르지만 x86이고 노트북 사양이라 운영과 다름
   - 운영 서버에는 부하를 걸지 않음. 카카오 진짜 로그인이 켜져 있고, 팀이 실제로 씀
2. **부하 도구**: k6(JS 스크립트, p95·p99·문턱 판정 내장, WebSocket 지원, 업계에서 흔함) vs Locust(Python, 팀이 아는 언어, `fake_runner.py` 재사용 쉬움). 처음 쓰는 기술이라 비교 설명 HTML을 먼저 드리고 고른 뒤 ADR-0014로 남김
3. **관측 범위**
   - 최소(추천): 요청마다 지연 로그 + `pg_stat_statements` + 부하 도구 요약
   - 확장: Prometheus + Grafana 대시보드(볼거리는 좋지만 VM 메모리·설정이 늘어남)
4. **가짜 데이터 크기**(가정, 시험용 값): 사용자 1만 명, 사람당 기록 100개(= 기록 100만 개, 속도 시계열 포함), 친구 0–50명, 인증 시도 기록 1–2개씩. 한 번에 다 넣지 않고 1천 → 1만 → 10만 → 100만 기록으로 늘리며 시간 변화를 봄

## 하는 것
1. **시험 환경**: 운영과 같은 `docker-compose.server.yml`에 `KAKAO_MODE=fake`(`k_숫자`로 로그인되는 기존 기능, 시험 서버 전용)·OCR 엔진 켬. 공개 주소는 열지 않거나 IP 제한
2. **가짜 데이터 넣기** `backend/scripts/seed_load.py`: 위 크기, 같은 시드면 같은 데이터, `COPY`로 빠르게. 기록 상태 분포(인증·미인증·인증 대기)와 날짜 분포를 정함
3. **지표**
   - API: 미들웨어가 요청마다 `경로 틀(/v1/runs/{id})·상태 코드·처리 ms·DB 쿼리 수`를 JSON 한 줄로 journald에 기록(사용자 ID·값은 안 남김)
   - DB: `pg_stat_statements`(쿼리별 호출 수·평균·최대 시간), 연결 풀 대기 시간
   - 서버: CPU·메모리(`docker stats`를 1초마다 저장)
4. **시나리오**(가상 사용자 수를 늘려 가며 각 5분)
   - S1 **앱 켜기**: 홈 → 기록 목록 → 친구 목록·달리는 친구·피드(읽기 위주)
   - S2 **달리기 한 번**: 맵 입장 → 러닝 시작 → 시계열을 여러 번 올림 → 종료 → 건너뛰기
   - S3 **실시간 같이 뛰기**: 맵 하나에 20명 WebSocket 접속, 초당 2번 상태 보냄(맵 개수를 늘림)
   - S4 **계기판 인증**: 합성 계기판 사진(`speedlab/ocr/console_synth.py`) 3장을 동시 1·2·4·8명이 올림
5. **기준선 기록** `docs/perf/README.md`: 시나리오별 p50·p95·p99, 초당 처리 수, 오류율(5xx·503), 지연이 꺾이는 가상 사용자 수(포화점), 그때 가장 느린 쿼리 5개. 원본(부하 도구 출력·지표)은 `data/perf/<날짜>/`, 시험 VM 사양·커밋·데이터 크기를 같이 적음
6. 기준선에서 병목 순위를 정해 다음 계획으로 넘김(예상 후보: S4 OCR 12초·503, S1 피드 정렬, S2 맵 입장 코스 행 잠금. **예상일 뿐, 측정으로 정함**)

## 판정
- 명령 한 줄로 같은 시험을 다시 돌려 같은 데이터·비슷한 수치(같은 조건 3번, p95 차이 10% 안)가 나옴
- 네 시나리오 모두 기준선 표가 채워지고, 원본이 `data/perf/`에 있음
- 운영 서버 코드 변경은 지연 로그 미들웨어 하나뿐이고, 켜도 운영 응답 시간이 눈에 띄게 늘지 않음(미들웨어 켜기 전후 `/v1/agreements` 비교)

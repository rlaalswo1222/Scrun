1브리지: Unity가 아이폰 기능을 부르는 통로

무슨 문제인가

우리 앱 화면과 로직은 Unity의 C#으로 짭니다. 그런데 권한 팝업, 에어팟 연결 감지, 카카오톡 로그인, 키체인(토큰을 안전하게 보관하는 곳) 같은 아이폰 기능은 애플 언어인 Swift로만 부를 수 있습니다. 두 언어는 서로를 직접 부르지 못하므로 그 사이에 통역 창구가 필요합니다. 이 창구를 "브리지"라고 부릅니다.

추천 설계의 3가지 요점

  1. 창구는 하나: C#이 부르는 함수는 scrun_call(번호표, 기능 이름, 내용) 하나뿐이고, 내용은 JSON 글자로 보냅니다. 기능마다 함수를 따로 만들면(권한 요청, 권한 상태, 에어팟, 카카오 로그인, 키체인 저장·읽기… 금방 20개) C#과 Swift 양쪽에 똑같은 선언을 맞춰 적어야 하고, 하나만 틀려도 아이폰에서 앱이 죽습니다. 창구가 하나면 새 기능을 추가할 때 이름만 늘리면 됩니다.
  2. 답은 번호표로 나중에: 권한 팝업처럼 사용자가 누를 때까지 기다려야 하는 일은 바로 답이 오지 않습니다. 그래서 번호표를 붙여 보내고, Swift가 끝나면 "7번 요청 결과는 허용"이라고 C#에 알려 줍니다(콜백). Unity 화면은 메인 스레드(Unity가 화면을 그리는 줄)에서만 고칠 수 있으므로, 받은 답은 큐에 넣어 두었다가 다음 프레임에 꺼냅니다.
  3. 에디터에서는 가짜: 같은 C# 모양(Native.Permissions)에 진짜(아이폰)와 가짜(FakeNative, 에디터) 두 구현을 둡니다. 지환님은 맥이나 아이폰 없이 에디터에서 "허용", "거부", "에어팟 끊김"을 눌러 화면을 만들 수 있습니다.

속도 센서는 이 창구를 쓰지 않습니다. 센서는 1초에 수십 번 값이 오는데, 창구를 그렇게 자주 오가면 느려집니다(Unity 문서도 매 프레임 여러 번 네이티브를 부르지 말라고 함). 그래서 Swift가 속도까지 계산해 두고, Unity는 매 프레임 숫자 하나만 읽습니다(S2).

다른 선택지

방식장점단점
창구 하나 + 번호표 콜백 (추천)기능을 늘리기 쉬움, 답이 바로 옴, 에디터 가짜와 모양이 같음처음에 큐·번호표 코드가 조금 필요(한 번만 만듦)
기능마다 함수 따로함수 하나하나는 단순양쪽 선언을 계속 맞춰야 하고 틀리면 아이폰에서만 죽음
UnitySendMessage (Unity 문서의 쉬운 방법)코드가 제일 짧음게임 오브젝트 이름으로 문자열만 보냄, 한 프레임 늦음, 이름이 겹치면 엉뚱한 곳으로 감

Xcode 프로젝트 종류는 뭔가

Unity로 iOS 빌드를 하면 Unity가 Xcode 프로젝트(아이폰 앱을 만드는 애플 도구용 폴더)를 만들어 주고, 맥의 Xcode가 그걸로 앱을 만듭니다. 이때 앱의 바깥 틀을 무슨 언어로 만들지 고를 수 있습니다.

Objective-C 틀 (추천, Unity 기본)Swift 틀
상태오랫동안 써 온 기본값Unity 6.5에 생긴 실험 기능
최소 iOS우리 설정 그대로(15.0)iOS 16으로 강제
우리 Swift 파일그대로 들어감(Assets/Plugins/iOS/에 두면 Unity가 복사)그대로 들어감

앱 바깥 틀이 Objective-C여도 우리가 짜는 코드는 전부 Swift입니다. 사용자에게 보이는 차이도 없습니다. 실험 기능에 앱을 걸 이유가 없으니 기본 틀을 추천합니다.

추천: 창구 하나 + 번호표 콜백, Objective-C 틀(Unity 기본). 정하면 ADR-0009에 적습니다.

2JSON 라이브러리

무슨 문제인가

서버와 앱은 JSON이라는 글자로 주고받습니다. 앱이 이걸 쓰려면 C# 데이터(객체)로 바꿔야 하고, 보낼 때는 반대로 바꿔야 합니다. 이 변환을 해 주는 도구가 JSON 라이브러리입니다.

{"resultType":"FAIL", "success":null, "error":{"code":"NICKNAME_DUPLICATED", "details":null}, ...}
→ C#에서 res.error.code == "NICKNAME_DUPLICATED"로 쓰고 싶음

Unity 기본 도구(JsonUtility)로는 왜 안 되나

Unity에 들어 있는 JsonUtility는 빠르지만, 게임 저장 파일용이라 할 줄 아는 게 적습니다. 우리 서버 응답에는 이런 것들이 계속 나옵니다.

  • 비어 있을 수 있는 값: "success": null, 키를 안 적은 사용자의 "heightCm": null → JsonUtility는 "없음"(null)과 0을 구분하지 못합니다. 키 0cm로 읽힐 수 있습니다.
  • 모양이 정해지지 않은 칸: 오류의 details(틀린 칸 이름 → 이유) → JsonUtility는 딕셔너리를 못 읽습니다.
  • 목록이 바로 오는 응답: 맨 바깥이 [...]인 JSON을 못 읽습니다.
선택지장점단점
Newtonsoft(Json.NET) (추천)C# 세계의 사실상 표준. Unity가 공식 패키지(com.unity.nuget.newtonsoft-json)로 배포. 위 문제를 다 처리JsonUtility보다 느리고 앱이 조금 커짐 → 우리 응답은 작아서 체감 없음(가설, 아이폰에서 확인)
JsonUtility + 우회추가 설치 없음null 칸마다 "있음/없음" 표시를 따로 달아야 함. 화면마다 실수가 생김
직접 만든 파서마음대로 고침만들고 테스트할 시간 낭비
추천: Unity 공식 Newtonsoft 패키지. 패키지 매니저에서 이름으로 하나 추가하면 끝입니다.
배울 자료: Unity: Newtonsoft Json 패키지 · Json.NET 공식 문서

3카카오 SDK 넣는 방법

무슨 문제인가

카카오 로그인을 하려면 카카오가 만든 라이브러리(SDK)를 앱에 넣어야 합니다. 카카오는 이 SDK를 Swift Package Manager(SPM), 즉 애플 공식 라이브러리 설치 방식으로만 배포합니다. 2.23.0부터 다른 방식(CocoaPods)은 지원을 끊었습니다.

문제는 Unity가 iOS 빌드를 할 때마다 Xcode 프로젝트를 새로 만든다는 점입니다. Xcode에서 손으로 "카카오 SDK 추가"를 해 두어도 다음 빌드 때 지워질 수 있습니다. 팀원 3명이 각자 빌드하면 각자 매번 손으로 해야 하고, 한 명만 빠뜨려도 "내 맥에선 되는데"가 생깁니다.

빌드 후처리는 Unity가 Xcode 프로젝트를 만든 직후에 자동으로 도는 C# 스크립트입니다. Unity 6에는 이 스크립트에서 SPM 패키지를 추가하는 함수(PBXProject.AddRemotePackageReferenceAtVersion)가 문서에 있습니다. 그래서 빌드 버튼만 누르면 누구 맥에서든 카카오 SDK가 들어갑니다.

같이 넣는 것이 하나 더 있습니다. 카카오톡 앱으로 로그인하면 카카오톡이 열렸다가 우리 앱으로 돌아와야 하는데, 이때 쓰는 주소(URL 스킴, kakao앱키://)와 "카카오톡이 깔려 있는지 확인해도 된다"는 허락 목록을 앱 설정(Info.plist)에 넣어야 합니다.

선택지장점단점
빌드 후처리로 자동 추가 (추천)누가 빌드해도 같음, 빠뜨릴 일 없음Unity 6.6 + 카카오 SDK 조합에서 실제로 되는지 아직 안 해 봄(가설) → 5번 단계에서 첫 빌드로 확인
Xcode에서 손으로 추가바로 됨빌드할 때마다, 사람마다 반복. 대신 Unity의 "덧붙이기(Append)" 빌드를 쓰면 손댄 게 남음 → 자동이 막혔을 때의 대안
추천: 빌드 후처리로 자동 추가. 막히면 손으로 추가 + Append 빌드로 임시 진행합니다.
배울 자료: 카카오: iOS SDK 시작하기(SPM 설치, 2.23.0부터 CocoaPods 중단) · Unity: PBXProject.AddRemotePackageReferenceAtVersion

4asmdef: 코드를 묶음으로 나누기

무슨 문제인가

Unity는 Assets 안의 C# 파일을 기본적으로 전부 한 덩어리(이름 Assembly-CSharp)로 컴파일합니다. 폴더에 asmdef 파일(Assembly Definition)을 하나 두면, 그 폴더 코드는 따로 떨어진 묶음이 됩니다.

왜 나누나

  1. 자동 테스트 때문(제일 큰 이유): "토큰이 만료된 요청 3개가 동시에 와도 재발급은 1번"처럼 손으로 확인하기 어려운 건 테스트 코드로 확인합니다. Unity 테스트 코드는 asmdef 묶음이어야 하고, 묶음은 기본 덩어리 코드를 쓸 수 없습니다. 그래서 테스트할 ApiClient도 묶음 안에 있어야 합니다.
  2. 경계가 생김: 앱 화면 코드가 섬 맵 내부 코드를 함부로 건드리지 못합니다. 쓰려면 명시적으로 연결해야 해서, 나중에 맵을 새로 바꿔도(11/24 이후 새 맵) 앱 화면이 덜 깨집니다.
  3. 컴파일이 빨라짐: 고친 묶음만 다시 컴파일합니다.

단점과 대처

묶음 안의 새 코드는 기본 덩어리의 기존 스크립트(ISpeedSource 등)를 쓸 수 없습니다. S1 앱 화면은 아직 그걸 쓰지 않으니 문제가 없고, S2에서 속도를 아바타에 연결할 때 기존 달리기 스크립트도 묶음(예: Scrun.Runtime)으로 옮깁니다. 지환님 화면 코드도 Scrun.App 폴더에 넣으면 됩니다. 이 규칙은 PR에 같이 적습니다.

추천: 새 앱 코드는 Scrun.App, 테스트는 Scrun.App.Tests. 기존 스크립트는 S2에 옮김.
배울 자료: Unity: Assembly definitions · Unity Test Framework

5노트북 서버로 http 허용

무슨 문제인가

지금 서버는 노트북에서 http://192.168.x.x:8000처럼 암호화 없는 http로 돌아갑니다. 그런데 아이폰(애플의 ATS 규칙)과 Unity(설정 "Allow downloads over HTTP", 기본값 막음)는 둘 다 암호화 안 된 http 접속을 기본으로 막습니다. 같은 와이파이에서 민재님 노트북 서버에 붙으려면 이걸 풀어야 합니다. 에디터에서 같은 PC의 localhost로 접속하는 건 Unity가 항상 허용하므로 문제가 없습니다.

선택지장점단점
개발 빌드에서만 허용 (추천, Unity 설정 "Allowed in Development Builds")설정 한 번, 출시 빌드는 자동으로 막힘개발 빌드 체크를 켜고 빌드해야 함(평소에 켜 둠)
항상 허용신경 쓸 게 없음출시 앱도 http가 열려 로그인 토큰이 암호화 없이 오갈 수 있음. 애플 심사에서 이유를 물을 수 있음
노트북에 https 인증서출시와 같은 조건노트북 IP가 바뀔 때마다 인증서를 다시 만들고 아이폰마다 인증서를 설치해야 함
11/09 아이폰에서 확인할 것(가설): ① Unity 설정이 아이폰 쪽 ATS 예외까지 같이 넣어 주는지 ② 같은 와이파이 기기에 접속할 때 iOS 14부터 뜨는 "로컬 네트워크 접근 허용" 팝업 → 앱 설정에 이유 문구(NSLocalNetworkUsageDescription)가 필요한지.
추천: 개발 빌드에서만 http 허용, 출시 빌드는 https만.
배울 자료: Unity: InsecureHttpOption.DevelopmentOnly · Apple: App Transport Security · Apple: NSLocalNetworkUsageDescription

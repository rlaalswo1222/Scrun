# 계획 0016: 진짜 서버 뼈대 — BL-44 "[기술] 백엔드 서버·DB 구축"

- 상태: **리뷰 후 수정 구현 완료** (11/08, 아래 "리뷰 후 수정" 9항목, 2차 리뷰 7건 반영, 테스트 165개 통과(설정·카카오 응답·닉네임 단위 + 동시 가입·동시 재발급·동시 로그인·유예·기기·상한 흐름)). 1차 완료 (2026-11-06. PostgreSQL(Docker) + Alembic 마이그레이션으로 테이블 20개·약관 목록, 로그인 5개 진짜 구현(가짜 카카오), 테스트 102개 통과(스텁 계약 + 로그인 흐름 11개). 이전 기록: 승인 · 구현 중, 민재 승인. 범위를 **DB + 테이블 20개 + 로그인 API 5개**로 줄임. 도구는 SQLAlchemy 2.0 + Alembic, 동기 방식. 요청 로그는 이번에 안 넣음)
- 왜: 지금 `backend/`는 고정 예시만 돌려주는 스텁. 로그인·기록·친구가 실제로 저장되려면 DB와 진짜 로그인 확인이 있어야 하고, 계정 삭제(BL-48)·운영 배포(BL-51)도 이 위에 올라간다
- 기준: [데이터 모델 v1](../api/data_model.md)(계획 0015), [API 공통 규칙](../api/README.md)·노션 API 명세(계획 0014), ADR-0002(FastAPI)·ADR-0008(PostgreSQL + Docker Compose, 제안)
- BL-44 인수 조건: ① 카카오 토큰을 확인하고 계정을 만든다(제공자별 연결 분리) ② 사용자·기록·인증·친구·목표를 저장·조회하는 API ③ 개발/운영 환경 분리 ④ 실시간 서버와 붙일 기반

## 방식: 스텁을 한 묶음씩 진짜로
- API 모양(요청·응답)은 그대로. 진짜가 된 묶음만 DB를 쓰고, 나머지는 스텁 응답 유지 → 앱 개발은 끊기지 않음
- 묶음 순서: **1) 기반 + 계정**(이번 계획) → 2) 러닝·인증·보상 → 3) 친구·피드·지표. 2·3은 각각 계획을 따로

## 1단계에서 하는 것
1. **로컬 DB**: `backend/docker-compose.yml`(PostgreSQL). 접속 정보는 환경 변수, `.env`는 git 제외하고 `.env.example`만 올림. 개발·테스트·운영 DB 분리(③)
2. **테이블 20개 전부 만들기**: 데이터 모델 v1 그대로, 마이그레이션(버전 붙은 DB 변경 기록)으로 관리. 사용자 삭제 시 CASCADE 포함
3. **진짜 로그인**: 카카오 토큰 확인 → `auth_identities`로 기존 사용자 찾기 / 없으면 가입용 토큰 → 가입 → 우리 access·refresh 토큰 발급(①). refresh 토큰은 해시로 저장, 로그아웃·재발급 때 폐기
4. **카카오는 바꿔 끼우기**: 테스트·개발은 가짜 카카오(토큰 `k_123` → 카카오 회원번호 123), 실제 호출은 카카오 개발자 앱 등록 뒤 환경 변수로 전환
5. **진짜가 되는 API(5개)**: 카카오 로그인·약관·가입·토큰 재발급·로그아웃. (11/06 민재: 닉네임 확인·내 정보·설정·계정 삭제 6개는 다음으로)
6. **테스트**: 테스트용 DB를 따로 띄워 pytest. 스텁 API 37개의 계약 테스트는 그대로 통과 + 로그인 5개는 진짜 흐름 테스트(처음 로그인 → 가입 → 다시 로그인 → 재발급 → 로그아웃 후 그 refresh 토큰 거절, 필수 약관 빠짐·닉네임 중복·만료 토큰)

## 하지 않는 것
러닝·인증·친구 등 나머지 API의 진짜 구현(2·3단계), 실시간 서버(BL-25, ④는 접속 정보 자리만), 배포(BL-51), 카카오 연결 끊기(BL-48), Apple 로그인

## 결정 필요
1. **DB를 다루는 도구**: SQLAlchemy 2.0 + Alembic(파이썬 표준, 마이그레이션까지) 추천 / 다른 선택지는 SQLModel(FastAPI 쪽에서 만든 SQLAlchemy 위 도구, 덜 성숙)
2. **동기 vs 비동기 DB 접근**: 동기 추천(코드가 단순, 우리 규모에선 성능 차이 없음)
3. **카카오 개발자 앱 등록**이 돼 있는지(안 돼 있어도 가짜 카카오로 1단계는 끝남)

## 리뷰 후 수정 (11/08 `/code-review` 10건, 민재 승인)
1. **설정 검사**: `JWT_SECRET`이 없거나 32자 미만이거나 예전 공개 기본값이면 서버가 시작하지 않음. `KAKAO_MODE` 기본값은 `real`, `fake`는 적어야만 켜지고, 모르는 값이면 시작 거부. `real`이면 `KAKAO_APP_ID`(숫자)가 꼭 있어야 함
2. **카카오 확인**: `GET /v1/user/access_token_info` 한 번으로 회원번호와 `app_id`를 받고, `app_id`가 우리 앱이 아니면 `INVALID_KAKAO_TOKEN`. 응답 JSON이 깨지거나 칸이 없으면 503
3. **가입 재시도**: 커밋할 때 충돌이 나면 다시 조회해서, 같은 카카오 계정이 이미 가입됐으면 그 계정 토큰을 주고, 닉네임이 겹치면 409. 친구 코드가 겹치면 3번까지 다시 시도
4. **refresh 동시 요청**: "아직 살아 있으면 폐기" 조건부 UPDATE 하나로 바꿈 → 교체는 딱 한 번만 일어남
5. **재사용 정책**: 30초 유예. 교체된 지 30초 안에, 그 대신 받은 새 토큰을 아직 안 썼으면 정상 재시도로 보고 새 토큰을 줌(안 쓴 그 토큰은 폐기하고 새 것으로 넘김 → 그 로그인에 살아 있는 토큰은 늘 하나, 재시도를 몇 번 해도 안 늘어남). 그 밖의 재사용은 탈취로 보고 **그 로그인(family)만** 폐기하고 다른 기기는 유지. 로그아웃한 토큰이 오면 그냥 401. 칸 추가: `family_id`, `device_id`, `revoked_reason`, `replaced_by_id`
6. **닉네임**: NFKC 정규화 → 앞뒤 공백 자름 → 2에서 12자 → 한글 완성형·영문·숫자·`_`만 허용. 금칙어는 대소문자와 `_`를 무시하고 검사
7. **닉네임 확인 API를 진짜로**: 가입 때와 같은 함수로 판정. 이유에 `INVALID`(형식) 추가. 로그인한 사람의 지금 닉네임은 사용 가능으로 봄
8. **재로그인**: 로그인·가입에 선택 칸 `deviceId`(iOS identifierForVendor)를 받음. 같은 기기의 예전 로그인은 폐기하고, 살아 있는 로그인은 사용자당 5개까지만 둠(넘으면 오래된 것부터 폐기). 사용자 행을 잠가 같은 사용자의 로그인은 한 번에 하나씩(동시에 와도 규칙 유지). 로그인할 때 그 사용자의 만료된 줄을 지움. 전체 정리 스크립트는 운영 배포(BL-51) 때 주기적으로 실행
9. **alembic**: 코드에서 부를 때는 로그 설정을 안 건드리고(`configure_logger=False`), 명령줄에선 `disable_existing_loggers=False`. 마이그레이션은 DB 주소만 읽음(`core/envfile.py`, 인증 비밀값 없이 돎)
- 2차 리뷰(11/08 `/code-review` 7건)도 반영: 유예 재시도 갈래 증식, 동시 로그인 잠금, 마이그레이션 설정 분리, `KAKAO_APP_ID` 숫자 검사, 가입 최종 형식 판정, 카카오 HTTP 클라이언트 잠금·종료 때 닫기, 사용자 확인 한 곳으로

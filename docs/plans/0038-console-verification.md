## 흐름
```text
종료(D-18, 민재) → E-02 촬영 안내(팁·예시) ─ "촬영 없이 마무리" → POST skip(SKIPPED) → 결과
                     └ 찍기 → E-03 카메라(민재 Swift, 브래킷 3장) ─ 남은 시간 끝 → E-10 → skip(TIMEOUT)
                                └ E-04 확인(다시 찍기 / 보내기) → E-05 읽는 중 → POST photo
                                      ├ VERIFIED → E-06 대조 표 + 인증 완료
                                      ├ UNVERIFIED(MISMATCH·UNSUPPORTED_CONSOLE) → E-07·E-08
                                      └ RETAKE_REQUIRED → E-09 다시 찍기(횟수·마감 안) / 포기 → skip(RETAKE_GIVEN_UP)
네트워크 없음(I-06): 사진은 폰에 두고 마감 안에서 다시 보내기
```

## 하는 것
1. **서버 인증 API를 DB와** (BL-18): `photo`·`skip`을(앱이 읽은 값을 받는 `reading`은 뺌: OCR은 서버(BL-17 ①), 추출값은 사용자가 못 고침(BL-17 ④). 노션 작업 표의 "판독값" API도 없앰) `runs`·`verifications` 표에 저장. 판정은 서버 한 곳(`core/verification.py`): 거리·시간을 센서 기록과 비교 → 허용 오차 안 VERIFIED, 넘으면 UNVERIFIED(MISMATCH), 못 읽음 RETAKE_REQUIRED(저장 안 함). 마감·재촬영 횟수·오차는 **서버 설정값**(코드에 고정 안 함). 마감은 앱이 보낸 `endedAt`이 아니라 **서버가 finish를 받은 시각**부터(앱이 꺼졌다 복구(BL-37)해 몇 시간 뒤 끝내도 촬영은 그 직후 가능하게). 끝난 러닝만, 한 번 정해지면 다시 못 바꿈, 같은 사진 다시 올리기 막기(바이트 해시만 저장). pytest: 세 결과 + 마감 지남 + 남의 기록 + 두 번 보내기
2. **서버 OCR** (BL-17): 엔진을 판정과 떼어 `ocr/` 한 모듈(사진 여러 장 → 칸별 숫자 + 신뢰도). 사진은 메모리에서만 읽고 바로 버림(디스크에 안 씀), 처리 시간 제한. 10/29 모델·코드가 없어져서(11/08 확인) **다시 만든다**: 공개 데이터 + 7세그먼트 합성 생성기 + 학습 + 채점 + 소수점·형식 규칙을 `speedlab/ocr/`에 남김. 엔진 고르기는 정할 것 1
3. **앱 화면**: E-02 안내 → `Native.Camera.ShootAsync`(0033) → E-04 확인 → 올리기 전에 가이드 영역만 잘라 줄임(브래킷 한 번 6.6–8.0 MB, 0033 실측) → E-05 → E-06–E-10. 흐름 판단은 순수 C#(`VerifyFlow`) + EditMode 테스트, 0035와 같은 방식. 에디터는 0033 가짜 카메라 + 로컬 서버로 끝까지
4. **기종별 인식률 표**(BL-17 ②, 작업 표 완료 기준): 상준이 모은 사진(BL-45) + 헬스장에서 앱 브래킷으로 찍은 사진. 사진은 저장소에 안 올리고(유리에 사람이 비침) 결과만 `console_ocr.md`, 기종·조명 메모

## 정할 것
1. **OCR 엔진** (새 결정 → ADR-0012): (가) 10/29처럼 YOLO 계열 검출 재학습 — 10/29에 세 기종 44칸을 맞힌 방식. 대신 Ultralytics는 AGPL-3.0이라 서버에서 써도 소스 공개 의무가 생길 수 있음(가설, 원문 확인 필요) (나) 같은 데이터·생성기로 Apache-2.0·MIT 검출기 학습 (다) 학습 없는 획 판별(`seg7_grid.py`) — 10/29 다른 기종에서 무너짐. **추천: 승인되면 (가)·(나) 비교 설명 HTML(라이선스 원문·출처 포함)을 먼저 드리고 고름.** 데이터·생성기·채점은 엔진과 상관없이 먼저 만듦
2. **허용 오차**(Q-01): 서버 설정값으로 두고 첫 값만 정함. 근거는 실측 센서 오차(10/29 다른 날 평균 0.52 km/h, 최대 1.28, 거의 모두 빠르게 → 8–10 km/h에서 평균 5–7%, 나쁠 때 13–18%). 제안(가설): **거리 15% 이내**, 시간은 계기판이 앱보다 먼저 켜지므로(카운트다운 전 걷기) **계기판 − 앱이 −30초에서 +5분**. 헬스장 사진이 모이면 다시 정함
3. **마감·재촬영**(Q-02·03): E-03 남은 시간 0:45(Figma), 인증 마감 = 종료 뒤 10분, 재촬영 3번. 모두 설정값
4. ~~먼저 필요한 것(민재)~~ → 11/16 해결: 달리기 API DB(#52 머지), 0033 PR은 민재가 오늘 연다. 앱 브랜치는 0033이 develop에 들어간 뒤 딴다(그 전엔 서버부터)
5. **시간 비교와 일시정지**(Q-33): 앱 시간은 일시정지를 뺀 값이고, 계기판은 기종마다 일시정지 중 시간이 멈추는지·정지하면 지워지는지 다름. → **11/16 지환 결정: 시간은 늘 판정하고 위쪽 허용만 쉰 시간만큼 넓힘**(계기판 − 앱이 −30초에서 +5분 + 쉰 시간. 쉰 시간 = (종료 − 시작) − 달린 시간). 처음 제안(시간을 빼기)은 시작·종료 틈이 몇 초만 생겨도 시간 검사가 꺼져서 버림. 기종 조사(BL-45) 뒤 다시
6. **BL-18 ① "종료 시각 비교"**: 계기판에는 종료 시각이 뜨지 않음 → "종료 직후에 찍었는가"를 서버 마감(종료를 받은 뒤 10분)으로 지킴. 마감이 지난 인증 대기 기록은 앱이 아무것도 안 보내도 조회에서 미인증(`run_access.verification_of`, 기록 조회 API(S5)도 이걸 씀)

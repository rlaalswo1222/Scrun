# 계획 0075: 요청 하나의 CPU 더 줄이기 + 0073 남은 재기

- 상태: **초안, 순서는 정함**(2026-11-26 민재): py-spy 먼저 → 확인 측정만(기준선 전체 다시는 안 함) → 후보 고치기. 11/26 밤 집 PC에서(낮엔 PC가 꺼져 있어 못 함). 운영 실측은 나중에 정함
- 담당: 민재
- 왜: 0073 뒤 집 PC 시험 서버에서 S1 200명 283/초, CPU 2개를 거의 다 씀(api 104% + db 63% + realtime 10%, [docs/perf/README.md](../perf/README.md#계획-0073-본편-프로세스-나누기--200명-처리량-185--283초54)). 코어를 늘릴 수 없으니 남은 길은 **요청 하나가 쓰는 CPU(api)와 DB 왕복(db)** 줄이기. 0073 리뷰 반영(서킷 브레이커·`/internal/*` 번호표 밖·번호표 12) 뒤로 다시 안 잰 것도 있음
- 결과물: 새 기준선(0073 최종) → 프로파일 → 고친 것별 전후 표. 응답 내용은 그대로

## 순서 (11/26 민재와 정함)
0. 집 PC 시험 서버를 develop `a85225c`로: 작업 트리 패치 지우고(`git checkout -- backend && git pull`) 이미지 다시 빌드, 기록 100만 그대로, 시험 전 `CHECKPOINT` (10분)
1. **py-spy 먼저**: api 프로세스 하나에 `py-spy --gil`, S1 200명 3분. 붙이면 처리량이 15%쯤 떨어져 숫자는 비교에 안 쓰고 **비율**로 후보 순서(특히 A 핑 몫, B 스레드 넘기기 몫)를 정함. 0073 때 본 큰 몫(가설, 그때 구성 기준): 동기 의존성·라우터를 스레드로 넘기고 받는 일(anyio), ORM + psycopg 32%, `current_user`가 매 요청 사용자를 읽는 몫 9%, HTTP 파싱·소켓 16%
2. **확인 측정만**(기준선 전체 다시는 안 함): S1 200명 1번·100명 1번(각 5분, 사이 60초). 200명이 지난 값(번호표 12, 283.9 / 282.5/초, [README](../perf/README.md#계획-0073-본편-프로세스-나누기--200명-처리량-185--283초54))과 10% 안이면 지난 200명 값을 기준선으로. 100명(번호표 12)은 전에 안 잼 → 이 한 번이 "전" 값, 한 번뿐이라 흔들림(지난 반복 9–21%) → **판정은 200명 처리량으로, 100명 p95는 참고**
3. 후보 고치기(아래 표)
4. 맨 끝에 리뷰 반영 확인: 실시간을 끈 채 S1 100명 2분(서킷 브레이커 뒤 홈 p50이 37 ms 근처로 돌아오는지, 전엔 80 ms), S3 100명 한꺼번에 ×3
- py-spy는 노트북에서도 비율은 잴 수 있음(같은 이미지, k6가 CPU를 나눠 써 숫자만 다름) → 집 PC가 안 될 때의 대안

## 고칠 후보 (py-spy로 순서를 정하고, 하나씩 고쳐 재기)
| | 지금 (코드 확인) | 고치는 방법 | 위험 |
|---|---|---|---|
| A. 연결 꺼낼 때마다 핑 | `session.py` `pool_pre_ping=True` → 요청마다 DB에 `SELECT 1` 한 번 더(S1 한 바퀴 8요청이면 8번) | 핑 끄고 `pool_recycle`(예: 5분) + 끊긴 연결 오류 한 번은 다시 시도 | DB를 다시 켠 직후 첫 요청들이 실패할 수 있음 → 테스트로 DB 재시작 흉내 |
| B. 스레드 넘기기가 요청당 여러 번 | 동기 의존성은 FastAPI가 **하나씩 따로 스레드에** 넘김. `home` = `get_db` 들어가기·나오기 + `current_user` + `get_now` + 라우터 = 4–5번 | IO 없는 것(`get_now`, 토큰 해석)은 `async def`로. `get_db`는 세션 만들기만 하므로(연결은 첫 쿼리 때) 넘기지 않게, 닫기는 라우터 스레드 안에서 | 이벤트 루프에서 DB를 건드리면 전체가 멈춤 → "루프에서 IO 없음"을 테스트로 고정 |
| C. `home` 쿼리 10번 | 주간 목표·레벨·달리는 친구·최근 기록·코스를 각 API 함수 그대로 모음 + `close_expired`(GET에서 쓰기) | 같은 함수를 쓰되 겹치는 조회(사용자 기록 집계 등)를 한 번에, `close_expired`는 쓸 게 있을 때만 커밋(지금도) → 횟수 재고 줄일 수 있는 것만 | 홈 값이 각 API와 달라지면 안 됨 → 기존 "같은 값" 테스트 |
| D. 매 요청 사용자 읽기 | `current_user`가 `db.get(User)` | 그대로 둠(탈퇴·정지 즉시 반영이 더 중요). 프로파일에서 크면 다시 봄 | — |

- A는 **py-spy에서 핑 몫이 작으면(몇 % 안) 안 함**(안정성을 줄이고 얻을 게 적음). 크게 나오면 넣되 DB 재시작 흉내 테스트를 통과할 때만 남김(11/26 Claude 추천, 민재에게 설명함)
- 고친 것마다 S1 200명 ×2·100명 ×1 → 표 한 줄. 효과가 측정 흔들림(10%) 안이면 되돌리고 기록만
- 운영 compose·번호표·풀은 안 바꿈(바꾸면 0073 판정 다시)

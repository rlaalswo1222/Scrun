# 계획 0065: 애플워치 앱 — 에어팟이 끊길 때 걸음 수 백업

## 맥 할 일
없음 — **중단**(11/25 민재 "워치는 넣지 말자"). 시험 앱 `ios/WatchSpike/`는 만들었다가 지움(맥 시험 안 함). 아래 1–5는 기록으로 남김

(옛 맥 시험 내용)
1. **설치**: 무료 팀으로 워치 앱이 깔리고 실행되는지(몇 번 막히면 오류 문구 그대로 적기)
2. **화면 꺼진 채 센서**: 손목을 내려 화면이 꺼진 상태로 2분 동안 `CMMotionManager` device motion 100 Hz가 계속 들어오는지, 실제 빈도·끊김. 세 가지로 비교
   - (a) 아무 세션 없이 → 멈추는지(멈추면 아래가 필요하다는 근거)
   - (b) `WKExtendedRuntimeSession`(physical therapy 종류, 건강 권한 없음, 최대 1시간)
   - (c) `HKWorkoutSession`(HealthKit, **심박 읽기는 요청하지 않고** 운동 쓰기만) → 무료 팀에서 HealthKit 기능이 켜지는지, 권한 화면에 뭐가 뜨는지 캡처
3. **아이폰으로 보내기**: `WatchConnectivity` `sendMessage`로 1초마다 작은 값(시각·팔 회전 폭·팔 주기)을 아이폰 앱으로. 아이폰 앱이 앞에 떠 있을 때(실제로는 Unity 앱이 계기판 위에서 켜져 있음) 지연·빠짐을 2분 동안
4. **배터리**: (b) 또는 (c)로 20분 돌렸을 때 워치 배터리 몇 % 줄었는지
5. 손목 표시 → **뺌**(11/25 민재: 시간·속도 모두 계기판에 있어 워치 화면에 띄울 필요 없음). 대신 **애플 자체 페이스**(`CMPedometer`)를 1초 요약에 실어 러닝머신 6·8·10·12 km/h 각 2분에서 계기판과 비교(11/25 추가, 사람별 치우침 기준이 될지 보는 것, 가설)

- 상태: **중단**(2026-11-25 민재 "워치는 넣지 말자") · 승인 11/21 · PC 분석 두 번(3번 확인 단서·새 특징) 모두 탈락
- 담당: 민재
- 왜: 11/21 헬스장(계획 0064, 1명·1회 → 가설)에서 9 km/h 세게 밟기 때 폰 충격 +51%인데 워치 팔 회전 +9% → 튀는 값을 가리는 독립 단서. 몸에 붙어 폰 위치·계기판 울림과 무관(다른 날 치우침에 강할 수도, 가설), 에어팟이 끊길 때 걸음 수 백업(팔 주기 = 두 걸음). 한계: 걸음 수 고정에서 10과 11 km/h는 못 가름(짧은 구간 1번)
- 우선순위: 주간 목표 리마인더(BL-46)를 뒤로 미룸(11/21 민재). 맵·아바타 연결, HUD 시간·약 속도, 친구 인증 기록은 그대로 먼저

## 하는 것
1. **맥 시험**(위). 무료 팀에서 설치·화면 꺼진 센서가 안 되면 워치는 종강 뒤 Apple Developer 가입 뒤로 미룸(그때까지 PC 분석만)
2. **ADR-0014**(ADR-0007 보충): 워치는 선택 기기(있으면 걸음 수 백업, 손목 표시 없음, 없어도 지금과 같음), 백그라운드 방식(b·c 중), 건강 권한 범위(심박은 안 읽음, 11/21 민재 결정), 개인정보처리방침에 들어갈 문장
3. **PC 분석**(`speedlab/exp/`): 0064 기록(11/21 워치, 11/22 에어팟 + 워치)으로 0064 걸음 수 규칙에 워치 팔 회전을 더했을 때 — "폰 충격이 오르는데 팔 회전이 그대로면 안 올림" — 세게 밟기가 더 막히는지, 10/29처럼 진짜 속도 변화는 안 막는지
4. **구현**(1·2·3 뒤)
   - 워치 앱(Swift, SwiftUI): 시작·정지는 아이폰 달리기 시작·끝을 따라감(워치에서 따로 누르지 않게), 화면은 연결·기록 상태만(손목 표시 없음, 11/25 민재)
   - 워치 계산: 100 Hz → 1초마다 팔 회전 폭·팔 주기만 아이폰으로(원본은 안 보냄)
   - 아이폰 Swift 플러그인: 워치 값 받기 → `SpeedEstimator.swift`·`fusion_live.py`에 같은 규칙(정답 파일 `speedlab/golden/` 다시, 맥 재생 비교)
   - Unity 빌드 후처리 `IosPostprocess.cs`에서 워치 타깃을 Xcode 프로젝트에 자동으로 붙이기(번들 `com.scrun.app.watchkitapp`), 손으로 Xcode 만지지 않게
   - 앱 설정에 워치 연결 상태(연결됨·없음)만, 워치 없으면 지금과 똑같이 동작

## 진행
- 11/25 Windows(민재): **3번 PC 분석** `speedlab/exp/watch_veto.py`(cadence_veto.py와 같은 틀·보정, 실행 `set PYTHONIOENCODING=utf-8 && .venv\Scripts\python speedlab/exp/watch_veto.py`). 규칙 "앱 값이 최근 6초 기준보다 0.3 km/h 넘게 오르는데 팔 회전 RMS가 기준보다 문턱만큼 안 오르면 안 올림"
  - 팔 회전 RMS(4초 창): 세트 2 8 → 9 km/h +5%, 10 → 11 km/h +4%, **세트 3 9 km/h 세게 밟기 +11%** → 세게 밟기가 진짜 속도 올림보다 팔을 더 흔듦, 비율 문턱으로 못 가름
  - 세트 3(실제 9 km/h 내내) 세게 구간 평균(최대) / 세트 2(진짜 8 → 11) 막은 틱: 지금 앱 10.54(11.00) / 0% · 걸음 수 Δ3 9.08(9.08) / 0% · 워치 5% 4초 10.42(10.86) / 17.6% · **둘 다(Δ3 + 워치 5%) 8.90(8.90) / 17.6%**. 반응 시간 중앙 2.8초는 다 같음(워치 2초 창만 3.9초)
  - 11/21 첫 보기와 다른 이유: 그땐 세게 밟기(팔 +9%)를 **8 → 10 km/h 두 단계 차이(팔 +24%)**에 대어 "약 +0.7 km/h"로 작아 보였음. 규칙은 0.5초마다 "지금 오르는 게 진짜냐"를 가려야 해서 비교 대상이 **한 단계(1 km/h) 올림**인데, 그때 팔은 +4–5%(10 → 11은 2초 창에서 +2%)뿐 → 세게 밟기 팔 변화가 진짜 한 단계 올림보다 큼. "팔 회전이 그대로면"이라는 전제부터 안 맞음(세게 밟아도 팔이 같이 커짐)
  - **판정: 3번 못 넘음**(세게 밟기는 조금 더 줄지만 진짜 속도 올림을 17.6% 막음) → 계획대로 워치는 **걸음 수 백업(팔 주기)만**(손목 표시도 11/25 뺌). 10/29 M·B는 워치 기록이 없어 영향 없음
  - 한계(가설): 1명·1회, 세게 밟기 15초 1번, 문턱(3·5·8%)·창(2·4·6초)을 같은 기록에서 고름, 세트 2는 보정에 쓴 기록, 단계 경계를 폰 충격으로 추정. 11/22 에어팟 + 워치 기록(아직 없음)으로 다시 볼 수 있음

## 무엇을
1. **보정 단계 API를 `ISpeedSensor`에 덧붙임**(계획 0020에서 미뤄 둔 것). 계산은 Swift가 하고 C#은 순서만 정한다
   ```csharp
   void BeginCalibrationStage(float speedKmh); // 안내 속도로 기록 시작(앞 5초 버림), 걷기·달리기는 센서가 판정
   CalStageResult EndCalibrationStage();   // 점 하나 추가 → Ok / NoSteps / Irregular / NotFaster / SensorLost
   string ExportCalibration();             // 보정점 JSON → 서버 model 칸
   bool LoadCalibration(string json);      // 서버에서 받은 것으로 시작
   void ClearCalibration();
   ```
2. **보정 흐름 `CalibrationFlow`**(화면과 분리한 상태 기계, EditMode 테스트 대상): 거치·센서 확인 → 사다리 7단계(2·4·6·8·10·12·14 km/h) → 저장 → 돌아갈 곳(코스 입장 다시 / 마이)
3. **보정 화면**(가로, UI Toolkit, 0018 앱 틀 위): 안내(A-11) · 거치·센서 확인(A-12) · 단계 진행(A-13: 목표 속도 큰 글씨, 남은 초, 단계 점 7개, 다음 속도 미리) · 단계 실패·다시(A-14) · 완료(A-15). 화면 번호와 내용은 구현 시작 때 Figma A-11–A-15와 맞춤(아직 Figma에서 확인 안 함). 모양은 상준 UI Kit이 오면 USS만 바꿈
4. **저장·불러오기**: 완료 → `PUT /v1/users/me/calibration` + 로컬 사본. 로그인 직후·앱 시작 때 `GET` → `LoadCalibration`. 저장 실패면 로컬 사본으로 계속 달리고 다음 실행 때 다시 올림
5. **진입점 두 곳**: 코스 입장이 409 `CALIBRATION_REQUIRED`면 보정 → 끝나면 입장을 다시 요청. 마이(H-09)에서 `CalibrationFlow.Start(returnTo)` 한 줄로 부름(버튼은 지환 화면)
6. **에디터 가짜**: `FakeSpeedSensor`가 가짜 사람(절편·기울기 + 흔들림)으로 보정점을 만들어 판정까지 흉내. Fake Native 창에 "다음 단계 결과 강제"(Ok·NoSteps·Irregular·NotFaster·끊김)

## 모두에게 같은 보정 사다리 (11/10 민재: 평소 속도를 묻지 않음, 1–15 km/h를 덮음, 3분 이하, 꼭대기 낮추지 않음)
분석 `speedlab/exp/calib_fixed.py`(11/10, PC). 우리 기록 2명·같은 날(낙관적) + SoundTrackDB 재분석(우리 실측 아님, 8에서 16 km/h)
| 질문 | 결과 |
|---|---|
| 두 보정점 **사이** 속도는 간격이 넓으면 나빠지나 | 거의 안 나빠짐. SoundTrackDB 간격 3.2 / 4.8 / 6.4 → 중앙 0.56 / 0.50 / 0.45(8.0은 0.75, n 10). 우리 M 간격 2 / 3 → 0.40 / 0.42 |
| 보정점 **바깥** 속도는 | 멀수록 커짐. 1.6 밖 0.88, 3.2 밖 1.23, 4.8 밖 1.78 |
| 촘촘한 사다리에서 전체 직선 vs 이웃 두 점 잇기 | 0.52 대 0.47, 비슷 → 전체 직선(지금 앱 모델) 유지 |
| 걷기 보정 | M (2, 4, 6) → 나머지 0.14, (4) 하나 0.22 / B (2, 6) 0.25, (4) 하나 0.29 |
| 1 km/h | 걸음이 잡힌 구간이 4개 중 1개(M 0/2, B 1/2) → 보정 문제가 아니라 **걸음 감지 문제**, 따로 풀어야 함 |

→ **결론(가설)**: 점을 많이 넣는 것보다 **사다리 양 끝을 1–15에 가깝게** 두는 것이 중요하다. 중간 점은 2–3 km/h 간격이면 충분하다. 남는 시간은 점을 더 넣지 말고 실패한 단계를 다시 하는 데 쓴다.
- **사다리(11/10 민재)**: **2 · 4 · 6 · 8 · 10 · 12 · 14 km/h**, 단계마다 15초(앞 5초는 속도 바꾸는 시간이라 버림 + 10초 잼). 7 × 15초 = 1분 45초 + 시작 안내 = **약 1분 50초**. 다음 속도는 단계 끝 3초 전에 미리 알리고, 버리는 5초 안에 버튼을 누름. 다시 하는 단계마다 15초씩 늘어남
  - 재는 시간 10초(11/10 민재): 우리 기록에서 버린 뒤 3·5·8·10·15·17초가 오차 차이 없음(M 0.38–0.40, B 0.41–0.50, calibration_design.md "구간 길이"). SoundTrackDB는 5초 0.60·10초 0.74·15초 0.61·20초 0.59·30초 0.54로 들쭉날쭉(30초 이상에서만 조금 나아짐). 헬스장 실험에서는 단계를 20초 이상 기록해 10초와 15초를 다시 비교
  - 분석상 중간 점은 정확도를 거의 안 올리지만, 2 간격은 안내가 단순하고("+2"), 한 점이 빠져도 구멍이 4 km/h에 그치고, 달리기 점이 4개라 걸음 수 기울기까지 이 사람 값으로 맞출 수 있음(지금 앱의 4점 이상 모델, 나은지는 실험으로 확인). 6과 8이 걷기·달리기가 갈리는 구간 양쪽을 잡음
  - 확인할 것: +2 km/h를 버튼으로 올리는 데 5초면 되는지(아이폰·러닝머신). 모자라면 7초 → 약 2분 45초
  - 사다리 숫자는 설정값 하나로 두어 실험 뒤 숫자만 바꿈
- **데이터가 없는 곳**: 1–2 km/h(걸음 감지. 건너뛰기가 없으니 2 km/h가 안 잡히는 사람은 보정을 못 끝냄 → 여러 명의 2 km/h 감지율을 재고, 낮으면 걸음 감지를 고치거나 바닥을 3으로), 6–8 km/h(걷기·달리기가 사람마다 갈림), 14–15. **헬스장 실험**(여러 명, 1–15를 1 km/h 간격으로, 사다리 후보 전부 포함)으로 확인 → 계획 따로(지환 헬스장 실험과 합칠지 상의)
- **ADR-0005와 다른 점**: 7단계 오름·내림 약 3분 → 7단계 오름만(2 간격) 단계 15초 약 1분 50초, 평소 속도 주변 → 모두 같은 사다리. 근거는 위 표와 calibration_design.md(내림 점을 섞으면 0.33 → 0.40, 1명). ADR-0005에 "추가 결정(11/10)" 줄을 넣고 헬스장 실험 뒤 다시 확인
- **멈춤**: 모두 끝까지 뛰는 것이 기본. 재는 중 걸음이 6초 없으면 실패로 안 세고 기다렸다가 그 단계부터 이어서(모은 점 유지). 그만두기 버튼을 누르면 저장 안 함, 지금 보정은 그대로
- **걷기 점을 실제로 씀**: 지금 Swift·`fusion_live.py`는 걷기를 공통 공식(−3.45 + 0.0732·spm)으로만 계산하고 걷기 보정점은 버림. 기울기는 공통 값, 절편만 이 사람으로 바꿈(calibration_design.md 걷기 1점 = 이 방식). **두 파일을 같이 고침**(SpeedEstimator.swift 머리 주석 규칙)
- **단계 실패 판정**: 한 단계에서 잰 10초의 값을 보정에 쓰면 안 되는 경우를 거름(잘못된 점 하나가 보정 전체를 틀어지게 함). 숫자는 가설, 아이폰에서 고침
  | 결과 | 앱이 보는 것 | 원인 예 | 앱이 하는 것 |
  |---|---|---|---|
  | NoSteps | 걸음 없음 | 옆 발판에 서 있음, 폰을 손에 듦 | "벨트 위에서 걸어 주세요" → 그 단계 다시 |
  | Irregular | 걸음 규칙성 0.3 미만 | 손잡이를 잡음, 비틀거림, 폰이 미끄러짐 | 그 단계 다시 |
  | NotFaster | ln(충격)이 앞 단계보다 0.05 넘게 커지지 않음 | 속도 버튼을 깜빡함 | "N km/h로 올려 주세요" → 그 단계 다시 |
  | SensorLost | 폰 가속도가 안 옴 | 앱이 백그라운드로 감, 화면 꺼짐 | 그 단계 다시 |
  - 걷기·달리기는 단계마다 미리 정하지 않고 센서가 판정한 대로 기록(6–8 km/h에서 걷는 사람도 정상)
  - **건너뛰지 않음(11/10 민재)**: 실패한 단계는 제대로 잴 때까지 다시 한다. 7점이 모두 모여야 완료이고 저장한다. 같은 단계가 두 번 연속 실패하면 원인별 도움 화면(폰 위치·손잡이·속도 버튼 확인)을 보여 주고 다시. 사용자가 그만두면(벨트에서 내려옴·화면의 그만두기) "보정 중단", 저장 안 함, 다음에 처음부터. 걷기·달리기 판정이 사람마다 다르므로 실패 판정에 쓰지 않음
- **안내**: 화면 글자 + 소리 → 결정 3
- **서버에 무엇을 저장하나**: API 본문의 `points`(속도·걷기/달리기·초)는 보여 주기용 요약, `model`(서버는 해석 안 함)에 Swift 보정점 원본 `{"version":1,"points":[{v,limp,cad,amp,running}]}`. 불러올 때 Swift가 다시 맞춤(`SpeedEstimator.load`와 같음). API 모양은 안 바뀜 → 지환에게 이 형식만 알림
- **기기**: `device`(예: `iPhone15,4`)가 지금 기기와 다르면 재보정 안내(ADR-0005 3번). 헬스장별 보정(ADR-0005 2번, 위치)은 이번에 안 함

1. 에디터 Play: 보정 없는 계정으로 코스 입장 → 보정 화면(가로) → 가짜 센서 시나리오로 6단계 → 완료 → 코스 입장 성공. Fake 창에서 NotFaster를 걸면 다시 안내가 나오고, 다시 하면 넘어감

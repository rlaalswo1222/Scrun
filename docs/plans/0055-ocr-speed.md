  - 같은 날 합성 계기판(2048×1097, 글자 영역 12개)은 한 장 2.4–2.5초, 3장 7.35초. 시간은 거의 전부 글자 영역 찾기·인식이고 글자 영역 수에 비례

  - 앱: E-05 고리(`.verify-spinner`)는 회전이 없는 정지 그림. "이 사진으로 인증"을 누르면 세 장 줄이기(`VerifyPhotos.Shrink`, 디코딩·JPEG 인코딩)가 메인 스레드에서 돌아 처음에 화면이 굳음. 503이면 원인과 상관없이 "읽는 곳이 바빠요"
  - 배포(`update.sh`)가 api 컨테이너를 새로 만들면 그전 로그가 사라짐(11/19 첫 실패 로그를 이것 때문에 잃음)

## 하는 것
1. **가이드 안만 보내기**(Swift, 정할 것 1): 찍은 사진을 가이드 사각형 + 여유(사방 15%)로 잘라 저장. 화면 좌표 → 사진 좌표는 `AVCaptureVideoPreviewLayer.metadataOutputRectConverted`. 계기판 밖 글자가 빠져 글자 영역 수(=시간)가 줄고 칸 찾기 오답도 줄 것(가설, 아래 확인으로 잼)
2. **서버: 0 EV부터 읽고, 같은 값으로 읽힌 사진이 두 장이면 멈춤**: 셋째 장을 건너뜀. 처음 안(첫 장이 읽히면 멈춤)은 합치기 규칙("읽힌 사진 값이 모두 같아야 READ", 11/17 지환)의 대조를 없애서 두 장 대조는 남김(구현하며 바꿈, 지환에게 알림). 못 읽은 사진이 끼거나 값이 갈리면 끝까지 읽음. 사진 순서는 앱이 0 EV에 가까운 것부터 보냄
3. **시간 제한**: 위 둘을 배포하고 실사진으로 다시 잰 뒤 정함(정할 것 2). 그때까지 오라클 `.env`의 `VERIFY_OCR_TIMEOUT_S=60` 유지
4. **앱 E-05**:
   - 고리를 실제로 돌림(UI Toolkit 회전 애니메이션, 화면이 숨으면 멈춤)
   - 줄이기를 메인 스레드에서 빼기: 1번으로 Swift가 잘라 저장하면서 긴 변 2048로 줄여 저장 → C# `Shrink`는 이미 작은 사진이라 디코딩 안 함(지금 코드 그대로)
   - 503 중 시간 초과는 "숫자를 읽는 데 시간이 너무 걸렸어요. 계기판이 가이드 안에 크게 들어오게 다시 찍어 주세요". 서버는 오류 코드를 새로 만들지 않고 `SERVICE_UNAVAILABLE`에 `details.reason: "OCR_TIMEOUT"`(옛 앱은 그대로 "바빠요"). 문구는 임시, 상준 확인
5. **로그가 배포를 넘어 남게**: 운영 compose의 api 로그를 `journald` 드라이버로(caddy는 접근 로그를 안 남기고 거의 안 새로 만들어 그대로)(컨테이너를 새로 만들어도 `journalctl CONTAINER_NAME=scrun-api-1`로 남음, 디스크는 journald 설정 한도)
6. **확인**: pytest(0 EV 먼저·멈춤, 오류 코드 나눔), EditMode(고리, 오류 문구), 아이폰 실사진 3번 이상: 사진 크기·글자 영역 수·묶음 시간(서버 로그)을 이 문서에 표로

## 정할 것
1. **잘라 보내기를 어디서**: (가) **Swift 촬영 화면에서 가이드 + 15%로 잘라 저장 (추천: 가이드 좌표를 정확히 아는 곳은 미리보기 화면뿐. 사진도 작아져 올리기·줄이기도 빨라짐. 지환 메모에도 "가이드 위치를 사진 자르기에")** vs (나) 서버가 계기판 영역을 찾아 자름(모델이 하나 더 필요, 시간이 더 듦)
2. **시간 제한 기본값**: (가) **1·2를 배포하고 실측으로 정함, 그동안 60초 (추천: 지금 15초로 돌리면 실사진은 거의 다 실패)** vs (나) 바로 30초로 고정

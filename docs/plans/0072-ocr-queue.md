# 계획 0072: 계기판 인증 OCR을 줄 세워 처리 — 몰려도 거절하지 않게

- 상태: **보류**(2026-11-26 민재 "OCR 쪽은 일단 나중에, 결정할 게 많네"). 아래 "정한 것"까지는 정했고, 방향(서버에서만 읽기 / 폰에서 읽고 서버가 뒤에서 확인 / 폰에서 다)을 먼저 정해야 함 → 끝의 "다시 시작할 때"
- 담당: 민재(서버), 앱 `VerifyScreen`은 지환과 정함(아래 "정할 것" 3)
- 왜: 계획 0070 S4([docs/perf/README.md](../perf/README.md#s4-계기판-인증-사진-3장-기록-100만-90초))에서
  - 읽기 프로세스가 2개뿐이고 **자리가 없으면 줄을 세우지 않고 바로 503**이라, 동시 4명이면 50%, 8명이면 80%가 거절됨
  - 운영 오라클 ARM은 사진 묶음 하나에 11.7–12.7초(11/25 운영 로그)라 **동시 3명 안팎부터 거절이 시작될 것**(가설, 운영에서 안 잼). 시연·헬스장처럼 2–3명이 같이 끝내고 인증하면 실제로 걸림
  - 인증 요청이 읽는 내내(운영 12초) 0071 번호표 1장과 요청 스레드를 쥠 → OCR이 몰리면 다른 API의 자리까지 줄어듦
  - 사용자는 "바빠요, 잠시 뒤 다시"만 보고 언제 될지 모름. 거절된 사진은 다시 올려야 함(LTE에서 수 MB)
- 결과물: 사진은 **받으면 줄에 넣고 바로 응답**, 앱은 "약 M초"를 보며 결과를 기다림. 줄이 아주 길 때만 거절

## 하는 것 (추천안 A: 접수 → 줄 → 결과 조회)
1. **접수** `POST /v1/runs/{runId}/verification/photo`: 지금처럼 확인(내 기록·마감·같은 사진·다른 기록 사진)한 뒤, 읽을 사진이면 메모리 줄에 넣고 바로 **202 + `status: READING`, `jobId`, 줄 위치, 예상 초**. 번호표·스레드는 접수가 끝나면 놓음
   - 사진은 지금처럼 **디스크에 쓰지 않음**(BL-17 ③): 줄도 메모리, 읽고 나면 버림
   - 줄 길이 상한(예: 20묶음, 사진 최대 12 MB × 20 = 240 MB 이하)을 넘으면 그때만 503 `OCR_BUSY` + 예상 대기
   - 같은 기록에 이미 읽는 중인 묶음이 있으면 새로 넣지 않고 그 `jobId`를 돌려줌(앱 재시도·두 번 누름)
2. **읽기**: 지금 `ReaderPool`(프로세스 2개)이 줄 앞에서부터 꺼내 읽음. 읽은 뒤 저장·판정(`decide`·`_save`)은 지금 코드 그대로, 기록 줄을 잠그고 다시 확인하는 순서도 그대로
3. **결과 조회** `GET /v1/runs/{runId}/verification/photo/{jobId}`: 읽는 중이면 `READING` + 위치·예상 초, 끝났으면 **지금 사진 응답과 똑같은 결과**(CONFIRM_REQUIRED·RETAKE_REQUIRED·UNVERIFIED). 앱은 1–2초마다 물음
4. **서버가 다시 뜬 경우**(배포·재시작): 줄이 메모리라 사라짐 → 조회가 `JOB_NOT_FOUND` → 앱이 같은 사진을 다시 접수(사진은 폰에 있음, 다시 찍기 횟수 안 씀). 마감은 지금처럼 **처음 사진이 도착한 때** 기준이라 다시 접수해도 손해 없게(접수 시각을 기록 쪽에 남김)
5. **앱** `VerifyScreen`: 202면 "인증 중" 화면에 "약 M초" → 조회 반복 → 결과는 지금 화면 그대로. 503 문구를 `details.reason`(OCR_BUSY·BUSY·DB_BUSY·OCR_TIMEOUT)으로 나눔(0071 리뷰에서 남긴 것도 같이)
6. **로그·측정**: 요청 로그에 줄 기다린 시간·읽은 시간을 나눠 남김(사진·숫자 값은 안 남김). S4 시나리오를 접수 → 조회로 바꿔 다시 잼

### 다른 안 B: 요청을 열어 둔 채 줄에서 기다림
- 앱은 거의 그대로(시간 제한만 늘림), 서버만 "바로 503" 대신 줄에서 최대 N초 기다림
- 단점: 운영에선 몇십 초짜리 요청이 됨 → 헬스장 LTE에서 끊기면 처음부터 다시, 줄 위치를 못 보여 줌, 기다리는 동안 번호표를 쥐지 않게 이 경로만 0071 밖으로 빼야 함. 출시 기준이면 A

## 이 계획으로 안 되는 것 (따로)
- **줄은 처리량을 늘리지 않음**: 거절을 기다림으로 바꿀 뿐. 운영은 프로세스 2개 × 묶음 12초 ≈ 분당 10묶음(가설) → 10명이 한꺼번에 끝내면 마지막 사람은 약 1분 기다림. 묶음 시간 줄이기(가이드 영역만 잘라 보내기, −1.5 EV 장 빼기 등)는 정확도와 같이 봐야 해서 지환과 따로
- 프로세스 여러 개(0073)로 가면 메모리 줄을 나눠 쓸 수 없음 → 그때 Redis로 옮김(사진을 디스크에 안 쓰는 규칙은 그대로)

## 정한 것 (11/26 민재)
1. **A(접수 → 조회)**
2. 줄 길이 상한 20묶음, 조회 간격 1.5초
3. 앱 `VerifyScreen`도 **민재가** 서버와 한 PR로 고침(지환에게 알림)
4. 화면엔 **예상 시간만**("약 30초"), 줄 위치는 안 보임
- 남은 질문(11/26 민재): 계기판을 폰에서 읽을 수는 없는지, 동시 100명 이상이면 어떻게 하는지 → 답에 따라 이 계획의 앱 쪽(기다리는 화면)이 바뀔 수 있음

## 판정 (집 PC 시험 서버, S4와 같은 조건: 사진 3장, 기록 100만, 90초)
| | 지금(0070 S4) | 목표 |
|---|---|---|
| 동시 4명 | 503 50% | 거절 0%, 모두 결과 받음 |
| 동시 8명 | 503 80% | 거절 0%, 줄 기다림 p95가 예상 초와 ±30% 안 |
| 처리량(성공 묶음/초) | 약 1.1 | 줄여지지 않음(10% 안) |
| OCR이 꽉 찬 동안 S1 50명 | 안 잼 | 서버 p95가 OCR 없을 때보다 10% 안(번호표를 안 쥐는지) |
- 서버를 읽는 중에 재시작 → 앱이 다시 접수해 결과를 받음(에디터 + 로컬 서버로 확인)
- 운영 배포 뒤 실물 사진 인증 1번: 결과·시간이 예전과 같음

## 다시 시작할 때 정할 것 (11/26 민재와 나눈 이야기)
1. **어디서 읽나**
   - (1) 지금처럼 서버만: 이 계획 그대로. 100명이 한꺼번에 오면 마지막 사람은 약 10분 대기(분당 약 10묶음, 가설). 마감은 도착 시각 기준이라 미인증으로 떨어지진 않음
   - (2) **하이브리드(Claude 추천)**: 폰이 읽고 → "맞아요" → 바로 "인증 완료"(낙관적 처리) → 서버는 이 계획의 줄에서 뒤에 다시 읽어 맞춰 봄, 다르면 그때 바꿈. 사용자 경험은 (3)과 같고 조작만 막음. 서버 부담이 크면 일부(예: 무작위 20%)만 확인
   - (3) 폰에서 다: 서버 OCR·줄·모델 받기 문제가 없어짐. 앱을 고치거나 요청을 가로채면 아무 값이나 인증됨(App Attest로 문턱만 높임, 무료 팀에서 되는지 확인 필요)
   - (2)·(3)은 11/06 "서버 처리" 결정과 ADR-0012를 바꾸므로 ADR 먼저. 아이폰에서 모델 세 개(YOLOX 3.7 MB·PP-OCRv5 검출 4.8 MB·한국어 인식 13.5 MB) 시간·결과가 서버와 같은지 맥에서 시험, 읽기 규칙(`field.py`·`seg.py` 약 450줄)을 Swift로 옮김(속도 계산을 옮긴 전례). 정확도는 지환과
2. **조작을 얼마나 막아야 하나**(기획): 인증 기록이 쓰이는 곳은 경험치·레벨·러닝복, 친구 비교, 공동 맵 인증 마크. 상금·공개 순위가 없으면 동기가 약함. 지금도 센서 값은 폰이 보내고, 화면에 띄운 가짜 계기판 사진은 서버도 못 거름
3. **하이브리드면** 아이폰(Core ML 16비트)과 서버(32비트) 값이 애매한 사진에서 갈릴 수 있음 → 다르면 바로 취소 말고 표시만, 갈리는 비율을 시험으로
4. **한 건 비용 줄이기**(어느 방향이든, 지환과): 양자화(INT8, 크기 약 1/4, 속도는 오라클에서 재야 함, 실사진 채점 세트로 정확도 전후 비교), 가이드 영역만 잘라 보내기, 사진 장수
5. **12/11 전에 할 것**: 하이브리드가 발표 전에 될지 불확실하면 이 계획 A를 그대로(기다리는 화면 포함) 먼저 — 줄은 하이브리드에서도 그대로 씀

계기판 숫자를 읽는 엔진 고르기

계획 0038 정할 것 1 → ADR-0012. 2026-11-16 지환. 서버(오라클)에서 계기판 사진의 거리·시간을 읽을 "숫자 검출 모델"을 고른다.

한 줄 요약
10/29에 잘 됐던 건 Ultralytics YOLO인데, 라이선스(AGPL-3.0) 때문에 서버에 올리면 서버 코드와 학습한 가중치까지 공개해야 한다는 것이 Ultralytics의 해석이다. 같은 데이터·생성기로 Apache-2.0 모델(YOLOX)을 먼저 학습하고, RF-DETR을 같은 채점으로 비교하는 것을 추천한다. YOLO11은 로컬 실험의 기준선으로만 쓴다.

1. 무엇을 고르는지

엔진은 아래 그림의 파란 칸 하나다. 나머지(자르기, 합성 생성기, 칸 묶기·소수점 규칙, 판정)는 어느 엔진이든 같고, 서버 코드도 core/ocr.py의 엔진 자리 하나만 바뀐다.

2. 우리가 아는 것 (10/29 시험)

  • 일반 OCR(Apple Vision, Windows OCR, Tesseract)은 7세그먼트를 거의 못 읽었다. 공개 모델·규칙 해독기도 다른 기종에서 무너졌다 (docs/product/console_ocr.md, 계획 초안 0011).
  • YOLO11n + 공개 데이터 + 합성 4,000장 + 소수점·형식 규칙이 세 기종 사진 3장의 44칸을 모두 맞혔다.
  • 단, 사진이 3장뿐이고 생성기·규칙을 그 사진의 실패를 보고 만들었다. 정확도는 아직 말할 수 없고, 새 기종 사진으로 다시 재야 한다.
  • 그때 모델·코드는 남아 있지 않다(11/08 확인). 어느 엔진을 고르든 데이터·생성기·채점은 다시 만든다.

4. AGPL이 우리에게 뜻하는 것

  • Ultralytics의 해석: 그 코드로 학습한 모델은 처음부터 학습해도 AGPL이다. 공개하지 않으려면 유료 Enterprise License가 필요하고, 지키려면 "파생 저작물 전체 소스(해당하면 모델 가중치 포함)"를 공개해야 한다 (Ultralytics License, 공식 포럼 답변).
  • AGPL 13조: 프로그램을 고쳐서 네트워크로 서비스하면 사용자에게 소스를 받을 길을 줘야 한다 (GNU AGPL v3 원문). 가중치까지 해당하는지는 다툼이 있고 판례는 못 찾았다. 법률 판단이 아니다.
  • 우리 저장소: 공개 저장소지만 LICENSE 파일이 없다. 그래서 지금은 "공개돼 있지만 모든 권리 보유" 상태다. (가)를 서버에 쓰려면 서버(최소 backend/)를 AGPL로 내고 가중치도 공개해야 하고, 나중에 비공개로 돌리거나 상용으로 가면 라이선스를 사야 한다.
  • 로컬에서 비교 실험만 하는 건(배포·서비스 안 함) 이 의무가 생기지 않는다(13조는 "고쳐서 원격 사용자와 상호작용할 때").

5. 추천과 순서

  1. 엔진과 상관없는 것 먼저: speedlab/ocr/에 공개 데이터 받기 → 7세그먼트 합성 생성기 → 칸 묶기·소수점 규칙 → 채점 스크립트.
  2. (나) YOLOX를 먼저 학습: 10/29와 같은 데이터 형식. 서버 2코어에서 가장 가벼울 것(가설).
  3. 같은 채점으로 비교: (다) RF-DETR-Nano와, 기준선으로 (가) YOLO11n(로컬에서만).
  4. 세 가지를 잰다. YOLOX가 기준선보다 확실히 못하면 그때 (다)나 (가)의 라이선스 비용을 다시 본다.
    • 칸 단위 정확도
    • 사진 단위로 거리·시간이 둘 다 맞은 비율
    • 오라클 ARM 2코어에서 3장 처리 시간

채점 사진: 학습에 안 쓴 새 기종(상준 BL-45 사진 + 헬스장 앱 브래킷 사진). 사람이 비친 사진은 저장소에 올리지 않고 결과만 console_ocr.md에.

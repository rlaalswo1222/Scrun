# 계획 0081: 계기판 OCR 한 장 시간 줄이기 — 글자 찾기 입력 크기 (BL-17 후속, 지환)

- 상태: **승인(11/26 지환: 계획 쓰고 로컬에서 먼저 재기 → 결과 보고 서버 반영 진행) · 구현(브랜치 `feat/ocr-det-speed`, 커밋·PR 전)**. 남은 것: 헬스장 실사진 확인, 오라클 배포 뒤 시간(민재). 실사진에서 찾은 정확도 문제는 계획 [0082](0082-ocr-field-fixes.md)
- 담당: 지환(OCR 엔진·정확도). 서버 시간 제한·배포·부하 시험은 민재(계획 0055·0070·0072)
- 이어서: 계획 0046(서버 엔진), 0055(빠르게 읽기 — 자르기·두 장 일치면 멈춤), 0072(OCR 줄 세우기, 보류)

## 왜
- 11/26 민재: 부하 시험 중 "OCR 인식이 왜 이렇게 오래 걸리냐, 앱으로 쓰면 분석에 10초 정도". 기록과 맞음: 11/19 아이폰 사진 3장(2048×1342, 글자 영역 10–11개) **묶음 11.70초**, 그중 PP-OCRv5 찾기·인식이 장당 3.11–4.25초, 7세그먼트는 장당 0.12–0.17초(계획 0055 표, 오라클 로그)
- 코드로 확인한 것: `ConsoleReader`는 RapidOCR 검출 크기를 기본값(`Det.limit_side_len: 736`, `limit_type: min`)으로 둠. `min`은 짧은 변이 736보다 **작을 때만 키우고 크면 그대로** → 앱 사진 2048×1342를 **원본 크기로 글자 찾기**
- 가설: 검출을 긴 변 960–1280으로 줄이면 찾기 시간이 크게 줄고, 숫자 읽기(7세그먼트·한국어 인식)는 원본에서 잘라 읽으니 정확도는 거의 그대로

## 하는 것
1. **단계별로 나눠 재기**: 지금 로그의 "찾기·인식"을 검출·인식으로 나눔(RapidOCR 결과의 단계별 시간). 어느 쪽이 큰지 보고 처방을 정함
2. **로컬 비교**(`speedlab/ocr/bench_det.py`): 합성 계기판 200장(`console_synth_b`, 고치며 안 쓴 것)을 앱 크기(긴 변 2048)로 키워서, 검출 설정 **지금(min 736) / max 1280 / max 960 / max 736**마다
   - 한 장 시간(중앙·90%), 검출·인식·7세그먼트 시간, 글자 영역 수
   - 사진 단위 맞음·틀린 READ·UNREADABLE(합성이라 **정확도 아님**, 바꾸기 전후 비교용)
   - 오라클처럼 onnxruntime **1스레드**로 잼(맥 M5라 절대값은 오라클보다 빠름, 비율만 봄)
3. 결과가 좋으면(시간 크게 줄고 틀린 READ가 늘지 않음) `ConsoleReader`에 검출 크기 설정 추가(코드 상수 `DET_SIDE`, 환경 변수는 안 씀: compose까지 배선해야 하고(0069에서 빠뜨린 적 있음) 값은 측정으로 정해 코드와 같이 바뀌는 것), 서버 로그에 검출·인식 시간 따로 → PR, 오라클 실측은 민재와
4. **헬스장 실사진**(오늘 또는 내일): 정확도가 줄지 않았는지 실물로 확인. 기종 여럿·각도·반사 섞어 앱으로 찍고 사진마다 계기판 실제 거리·시간을 `truth.json`에 적음. 원본·조건은 `data/`

## 판정
- 바꿀 값: 합성 비교에서 **틀린 READ가 지금보다 늘지 않고** 맞음이 2%p 넘게 떨어지지 않는 것 중 가장 빠른 것. 실사진에서 다시 확인 뒤 확정
- 숫자는 이 문서 "진행"과 `docs/product/console_ocr.md`(실측일 때)

## 안 하는 것
- 3장 동시 읽기(몰릴 때 다른 사람 자리를 뺏음 → 0072 줄 세우기와 같이), 폰에서 읽기(0072 방향 결정·ADR-0012 변경), 모델 바꾸기·다시 학습

## 위험 (가설)
- 계기판이 사진에서 작게 찍히면 줄인 그림에서 글자를 놓침 → 실사진에서 확인. 앱 자르기(가이드 + 15%)로 계기판이 크게 들어온다는 전제
- 합성 계기판은 실물보다 깔끔해서 줄여도 잘 읽힐 수 있음 → 합성은 비교용일 뿐

## 진행
- 11/26 로컬 비교(맥 M5, onnxruntime 1스레드, `bench_det.py`, 결과 `speedlab/ocr/runs/bench_det/`(git 밖)). 합성 계기판 200장(`console_synth_b`)을 앱 크기(2048×1097 등)로 키움. **합성이라 맞음 비율은 정확도가 아님**

  | 검출 설정 | 한 장(중앙) | 90% | 검출 | 인식 | 7세그 | 맞음 | 틀린 READ | UNREADABLE |
  |---|---|---|---|---|---|---|---|---|
  | min 736(지금) | 1.07초 | 1.24초 | 0.63 | 0.37 | 0.04 | 150 (75.0%) | 1 | 49 |
  | max 1280 | 0.67초 | 0.77초 | 0.25 | 0.37 | 0.04 | 155 (77.5%) | 0 | 45 |
  | **max 960** | **0.55초** | 0.64초 | 0.14 | 0.37 | 0.04 | 156 (78.0%) | 0 | 44 |
  | max 736 | 0.50초 | 0.58초 | 0.08 | 0.37 | 0.04 | 152 (76.0%) | 0 | 48 |

  - 지금은 한 장 시간의 약 60%가 검출. max 960이면 검출 0.63 → 0.14초, 한 장 **1.07 → 0.55초(약 절반)**. 글자 영역 수(중앙 10개)는 같음
  - 결과는 그대로이거나 조금 나음(틀린 READ 1 → 0). 다만 사진별로는 바뀜: max 960에서 못 읽음 → 맞음 17장, 맞음 → 못 읽음 12장. 경계에 있는 사진이 흔들리는 것이라 실사진으로 다시 봐야 함
  - 오라클 예상(**가설**): 11/19 실사진은 오라클에서 장당 3.1–4.3초로 맥 합성(1.07초)의 약 3–4배. 같은 비율이면 장당 약 2초, 묶음(2–3장) 11.7초 → 약 4–6초. 배포 뒤 서버 로그로 확인
  - 줄인 뒤엔 **인식(0.37초, 한 장의 약 2/3)**이 다음으로 큼. 글자 영역마다 한국어 인식을 돌리는 것 → 다음 후보(이 계획 밖)
- 11/26 인터넷 사진 1장(JACO FITNESS 빨간 LED 7세그먼트 4칸, 500×375, 로컬 `data/web/jaco_01.png`): 원본·2048로 키움 × min 736·max 960 **모두 UNREADABLE**(틀린 READ 없음)
  - 라벨이 표시창 아래 아주 작은 글자(원본에서 약 10 px)라 사람도 셋째 칸이 거리인지 칼로리인지 못 읽음 → 라벨을 하나도 못 찾아 거리·시간 후보 0개. 정답을 못 정하는 사진이라 채점에서 뺌
  - 7세그먼트: 흐름 안에서 "1406" → 16, "1786" → 1.6으로 잘못 읽음. 손으로 꼭 맞게 잘라 4배로 키우면 1406·1786을 맞게 읽음 → 모델보다 **해상도·자르기** 문제(가설). 표시창 앞의 꺼진 자리(희미한 8)도 섞임
  - 2048 + min 736에서는 시간·거리 두 칸이 한 영역으로 붙어 찾힘("14n6I7AA"), max 960에서는 따로 찾힘(1장이라 참고만)
  - 인터넷 사진은 긴 변 1000 px 넘는 것만 쓰기로(앱은 2048)
- 11/26 인터넷 사진 2(영문 라벨 빨간 LED, 474×631, 로컬 `data/web/simon_01.png`, 정답 TIME 00:06·DISTANCE 0.00): 네 조건 **모두 UNREADABLE**, 찾은 것(고칠 후보, 아직 안 고침):
  1. **라벨 글자 오인식**: DISTANCE → "DISTACE"·"DUSTACE"·"DASTACE"(474 min 736에서만 거리 라벨로 잡힘). 지금 `label_kind`는 낱말이 그대로 들어 있어야 함 → 긴 라벨 낱말(DISTANCE·CALORIE 등)은 글자 1–2개 틀려도 받기
  2. **점·콜론 빠짐**: 거리 0.00 → "000", 시간 00:06 → 7세그 "0006"(4자리라 숫자로 안 봄)·인식 "00:86". 둘을 합치면(7세그 숫자 + 인식 글자의 점·콜론 자리, 숫자 개수가 같을 때만) 00:06
  3. **잘못 읽은 시간**: 2048 + max 960에서 7세그 "00.08" → 시간 8초(정답 6초). 거리까지 찾았으면 틀린 값으로 READ. 7세그와 인식이 둘 다 숫자인데 다르면 어떻게 할지 정해야 함(지금은 7세그 우선). 읽은 값 확인 단계(계획 0045 "맞아요/틀렸어요")가 마지막으로 거름
  4. **잡글자가 많으면 인식이 느림**: 버튼·물결무늬·워터마크까지 글자 영역 약 30개 → 인식 0.86–1.37초(합성 0.37초). 앱 가이드 자르기 뒤에도 버튼 줄이 남는 기종이면 같은 문제 → 인식 줄이기가 다음 후보

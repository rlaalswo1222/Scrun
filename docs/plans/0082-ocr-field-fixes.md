# 계획 0082: 계기판 칸 읽기 정확도 — 라벨 오인식·점·콜론·두 읽기 불일치 (BL-17 후속, 지환)

## 왜 (11/26 인터넷 계기판 사진 2장, 로컬 `speedlab/ocr/data/web/`, 출처 불명이라 저장소에 안 올림)
두 장 모두 UNREADABLE(틀린 READ는 없음). 둘 다 긴 변 500–630 px라 앱 사진(2048)보다 흐림 → 1·2번 일부는 해상도 탓일 수 있음(가설)
1. **라벨 글자 오인식**(사진 2, 영문 라벨): DISTANCE → "DISTACE"·"DUSTACE"·"DASTACE". `label_kind`는 낱말이 그대로 들어 있어야 해서 네 조건 중 한 번만 거리 라벨로 잡힘
2. **점·콜론 빠짐**(사진 2): 거리 0.00 → 두 읽기 모두 "000". 시간 00:06 → 7세그먼트 "0006"(점·콜론 없는 4자리라 숫자로 안 봄), 한국어 인식 "00:86"(숫자 틀림)
3. **불일치를 못 잡음**(사진 2, 2048 + 검출 960): 7세그먼트 "00.08", 인식 "00:86". 인식 쪽은 초가 60을 넘어 시간으로 해석이 안 돼 후보에서 빠지고, 7세그먼트 8초(정답 6초) 하나만 남음 → `decide`의 "한 칸을 두 읽기가 다르게 읽으면 못 읽음"이 작동하지 않음. 이 사진은 거리 0이라 값끼리 확인에서 걸렸지만, 거리가 정상이면 틀린 값으로 READ
4. **7세그먼트 자르기**(사진 1, 빨간 LED): 흐름 안에서 "1406" → 16, "1786" → 1.6. 표시창만 꼭 맞게 잘라 4배로 키우면 1406·1786을 맞게 읽음 → 모델보다 자르는 범위·해상도 문제(가설). 숫자 앞 꺼진 자리(희미한 8)도 섞임
5. (참고) 라벨이 사람도 못 읽을 만큼 작은 기종(사진 1): 정답을 정할 수 없어 채점에서 뺌. 앱 사진 크기에서 다시 봄

## 하는 것 (후보, 실사진을 본 뒤 확정)
1. **긴 라벨 낱말은 글자 1–2개 틀려도 받기**: DISTANCE·CALORIE 등 6글자 넘는 낱말만 편집 거리로(짧은 KM·TIME·분은 그대로, 엉뚱한 글자가 라벨이 되지 않게). STRONG_OTHER(SPEED·PACE…)도 같은 규칙이어야 "SPEEO"가 그 밖으로 남음
2. **두 읽기 합치기**: 숫자 개수가 같고 한쪽만 점·콜론이 있을 때만, 7세그먼트 숫자 + 인식 글자의 점·콜론 자리("0006" + "00:86" → "00:06")
3. **불일치 규칙 보강**: 두 읽기가 둘 다 숫자를 냈는데 숫자열이 다르면(해석이 되든 안 되든) 그 칸은 애매 → UNREADABLE. 2번으로 합쳐진 경우는 예외
4. **7세그먼트 자르기**: 검출 상자 여백(`_crop` pad)·꺼진 자리 처리를 실사진으로 비교. 모델 다시 학습은 하지 않음(필요하면 따로)
5. 규칙 테스트(`test_console_field`)에 위 사례를 글자 수준으로 추가(사진은 저장소에 안 올림)

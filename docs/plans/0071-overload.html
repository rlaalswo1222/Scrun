몰려도 멈추지 않는 서버

계획 0071 설명. 2026-11-25 부하 시험(계획 0070)에서 본 멈춤이 왜 생기고 어떻게 막는지, 처음 듣는 말(연결 풀·세마포어·백프레셔·큐·프로세스)을 식당에 빗대어.

한 줄 요약
지금 서버는 주문을 무한히 받아 주방(스레드 40)과 화구(DB 연결 15)가 서로 기다리다 멈춘다. 입구에서 번호표를 화구 수만큼만 주고(세마포어), 번호표를 못 받으면 바로 "잠시 뒤 다시"(503)라고 말하면, 받은 손님은 제때 받고 폭주가 끝나면 바로 정상으로 돌아온다.

1. 식당으로 본 서버

서버식당우리 값
요청손님 주문앱 화면 하나 열 때 8개쯤
스레드요리사최대 40명(FastAPI 기본)
DB 연결(연결 풀)화구 — 미리 켜 두고 빌려 쓰고 돌려줌5 + 바쁠 때 10 = 최대 15개, 못 받으면 30초까지 기다림
프로세스지점 — 요리사·화구·수첩이 따로1개(CPU 2코어 중 한 코어만 씀)
Caddy입구 안내원운영 서버 맨 앞(HTTPS)

2. 왜 멈췄나 — 서로 기다리기(교착)

요청 하나는 여러 단계(로그인 확인 → 본 처리)를 거치는데, 단계마다 요리사를 새로 배정받는다. 첫 단계에서 화구를 잡으면 요청이 끝날 때까지 쥐고 있다.

둘 다 상대를 기다리다 30초 뒤 포기(500). 손님이 이미 떠난 주문도 끝까지 만들어서, 폭주가 끝나도 8분 넘게 밀린 주문을 처리했다(S1 200명 뒤 50명 시험 두 번 실패). 11/25 #138로 "첫 단계부터 화구 잡기"는 없앴지만, 요리사(40) > 화구(15)인 구조는 남아 한 번은 재현됐다.

3. 막는 법 ① 입구 번호표 — 비동기 세마포어

세마포어 = 동시에 들어갈 수 있는 수를 정한 번호표 묶음. 비동기 = 기다리는 동안 아무 자원(스레드·연결)도 쥐지 않음(파이썬 asyncio.Semaphore). 주방 안 주문 수가 화구 수를 넘지 않으니 교착이 구조적으로 안 생긴다.

4. 막는 법 ② 빨리 거절 — 백프레셔

지금바꾸면
주방이 꽉 찼을 때주문을 계속 받음 → 다들 30초 기다리다 500입구에서 W초(예: 2초) 안에 번호표를 못 받으면 바로 503 + "1초 뒤 다시"(Retry-After)
손님이 떠난 주문끝까지 만듦 → 회복 8분기다리는 동안 연결이 끊겼으면 버림
폭주가 끝나면밀린 주문 처리하느라 몇 분몇 초 안에 정상(판정: 30초 안)

백프레셔 = 뒤쪽(주방)이 감당 못 할 때 앞쪽(손님)에게 "지금은 못 받아요"라고 압력을 되돌려 주는 것. 받은 주문을 제때 처리하는 게 모든 주문을 늦게 처리하는 것보다 낫다. 앱은 이미 서버 오류를 "다시 시도" 화면으로 보여 준다.

5. 다음 계획에서 쓸 말 — 접수와 처리 분리, 큐(0072 OCR)

지금은 카운터에서 12초 서서 기다리고, 직원이 2명이라 동시 4명이면 절반을 돌려보낸다(503, S4). 세탁소 번호표처럼 맡기면 번호를 주고 순서대로 처리한다. SKIP LOCKED = "다른 일꾼이 잡은 줄은 건너뛰기"라 두 일꾼이 같은 사진을 읽지 않는다.

6. 다다음 계획에서 쓸 말 — 프로세스와 실시간 분리(0073)

프로세스마다 기억(메모리)이 따로다. 일반 API는 매번 DB에서 읽어 늘려도 되지만, 실시간 방 상태는 프로세스의 수첩(파이썬 변수)에 있어 나누면 서로 안 보인다. 실시간만 한 프로세스에 모으면 수첩이 하나라 Redis 없이 된다(서버를 여러 대로 늘릴 때 Redis가 필요).

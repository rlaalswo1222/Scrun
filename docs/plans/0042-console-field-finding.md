# 계획 0042: 계기판 사진에서 거리·시간 칸 찾기와 이름 붙이기 (BL-17, S4 지환)

- 상태: **승인(11/17 지환: 정할 것 1 B + A 보조, 2 다시 찍기, 3 센서로 칸 고르기 금지 → 0038에 한 줄) · 구현 중** (흐름·합성 채점까지, 실사진 채점 전)
- 담당: 지환. 엔진·채점은 `speedlab/ocr/`(ADR-0012), 서버 연결은 `backend/app/core/ocr.py`
- 비교 그림: [`0042-console-field-finding.html`](0042-console-field-finding.html)

## 지금 (코드·기록에서 확인)
- YOLOX-Nano가 **잘라 놓은 칸 하나**의 7세그먼트 글자를 읽는다(공개 test 93.1%, 합성 99.0%, 정확도 아님, `speedlab/ocr/README.md`). 사진 전체에서 어느 칸이 거리·시간인지는 아무도 정하지 않는다
- 10/29 시험(`docs/product/console_ocr.md`): 그 러닝머신은 **시간을 "1.00"(점)으로** 보여 줌 → "콜론이면 시간" 같은 형식 규칙만으로는 틀림. 인쇄된 라벨("시간", "km")은 일반 OCR(Windows)이 잘 읽음
- 서버 판정(0038)은 거리·시간을 못 읽으면 UNREADABLE → 다시 찍기(3번), 지원 안 함은 UNSUPPORTED_CONSOLE

## 방법 비교 (자세한 그림은 HTML)
| | 방법 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| A | 형식 규칙만(콜론 → 시간, 소수 둘째 자리 → 거리) | 모델 추가 없음 | 10/29 기종에서 이미 틀림. 속도 "8.0"·경사 "1.5"와 헷갈림 |
| **B** | **글자 영역 찾기 + 라벨 읽기**: PP-OCRv5 검출(DBNet)로 사진의 글자 영역을 모두 찾고, 숫자 칸은 우리 YOLOX가, 라벨·LCD 글자는 PP-OCRv5 한국어 인식이 읽어 가장 가까운 라벨로 이름 | 기종을 몰라도 됨, LCD·터치스크린 숫자도 같은 길, 모델 둘 다 Apache-2.0 | 서버 모델 약 20MB·처리 시간 늘어남(오라클에서 잼), 라벨이 그림(아이콘)뿐인 기종은 A로 |
| C | 칸 검출 모델 따로 학습(거리·시간·기타) | 한 번에 끝남 | 기종마다 다른 실사진 수백 장에 상자를 쳐야 함. 지금 없음 |
| D | 사람이 지정(찍을 때 가이드 칸에 거리 숫자 맞추기, 또는 사진에서 탭) | 가장 확실 | 사용자 할 일 늘어남, Swift 촬영 화면(민재)·Figma 바꿈, 11/17 "E-04는 사진만"과 다름 |
| ✕ | 센서 값과 가장 가까운 칸 고르기 | 쉬움 | **안 씀**: 인증이 센서를 확인하는 것이라 센서로 칸을 고르면 독립성이 깨짐(다른 칸이 우연히 맞으면 통과) |

## 하는 것 (추천: B + A를 보조로)
1. `speedlab/ocr/field.py`: 사진 → PP-OCRv5 검출 → 영역마다 (7세그먼트면 YOLOX, 아니면 PP-OCRv5 인식) → 라벨(거리·DIST·km / 시간·TIME·min)과 가까운 숫자를 짝지음 → 라벨이 없으면 A 규칙 → **거리·시간 후보가 하나씩일 때만 READ**, 둘 이상이거나 없으면 UNREADABLE(추측하지 않음)
2. 합성 계기판 전체 그림(라벨 한·영, 칸 4–6개, 시간 점·콜론 둘 다)으로 흐름 시험. 점수는 정확도가 아님
3. 채점: 학습에 안 쓴 새 기종 실사진에서 **사진 단위로 거리·시간이 둘 다 맞은 비율**(ADR-0012 채점 2). 사진은 상준 BL-45 + 헬스장(0033 브래킷)
4. 오라클 ARM 2코어에서 브래킷 3장 처리 시간(서버 OCR 시간 제한 15초 안)
5. 문서: `speedlab/ocr/README.md`, ADR-0012 참고 줄, `docs/product/console_ocr.md`(실측이 생기면)

## 정할 것
1. 방법: **B + A 보조(추천)** / A만 / D(사람 지정)
2. 애매할 때(거리 후보 둘): **UNREADABLE → 다시 찍기(추천)** / 미인증 저장
3. 센서 값으로 칸 고르기 금지를 0038 "독립성 원칙"에 한 줄 더함(추천)

## 위험·모르는 것 (가설)
- 값이 번갈아 나오는 한 칸(스캔 모드) 기종: 라벨 옆 표시등으로 지금 값을 알아야 함 → 실사진 보고 정함. 사진 3장(브래킷)이 도움이 될 수 있음
- PP-OCRv5 한국어 인식 모델은 PaddleOCR 공식 표의 정확도 88.0%(그쪽 데이터)일 뿐 계기판 라벨 정확도는 모름
- 10/29처럼 라벨이 칸 위·아래·옆 어디에 있는지 기종마다 달라 "가장 가까운 라벨"이 틀릴 수 있음

## 진행 (11/17)
- `speedlab/ocr/field.py`(칸 찾기·이름 붙이기), `console_synth.py`(계기판 전체 합성), `eval_console.py`(사진 단위 채점). RapidOCR 3.10.0(PP-OCRv5 검출 mobile 4.8 MB + 한국어 인식 mobile 13.5 MB, `MODEL_LICENSES.md`: 모델 Apache-2.0, 저작권 Baidu·PaddleOCR)
- 합성 계기판 채점(**정확도 아님**, 생성기가 만든 그림): 고치며 쓴 200장 85.0%(틀린 READ 1), **새로 만든 200장 80.5%(틀린 READ 1, UNREADABLE 38 중 아이콘뿐 계기판이 대부분)**. 한 장 처리 약 450 ms(맥 M5, 2스레드) → 브래킷 3장 약 1.4초, 오라클 ARM은 따로 잼
- 합성으로 찾아 고친 것: 글자 영역 찾기가 소수점·콜론·7세그먼트 "1" 틈에서 숫자를 쪼갬 → 쪼개진 모양일 때만 다시 합침(옆 칸까지 합치지 않게) / 오른쪽 라벨은 단위(km·min…)일 때만(그 밖은 다음 칸 라벨) / 형식 규칙(A)은 라벨이 하나도 없는 계기판에서만(라벨 있는 계기판에서 페이스 3:33을 시간으로 잡아 틀린 READ) / 인식 글자의 7세그먼트 혼동(S→5 등)은 숫자 영역에서만 / 계기판 값끼리 확인(평균 속도 1–30 km/h, 센서 아님)
- 남은 틀린 READ는 끝자리 0.01 km를 놓친 것(서버 허용 오차 15% 안). 남은 실패: 라벨이 숫자 아래인 계기판에서 윗줄 숫자와 짝이 바뀜, 아이콘뿐인 계기판(시간·페이스 둘 다 콜론 → 다시 찍기)
- 다음: 새 기종 실사진(상준 BL-45 + 헬스장 브래킷)으로 채점 → 오라클 ARM 시간 → 서버 엔진(`core/ocr.py`, 자식 프로세스) 연결

로깅·모니터링 고르기

계획 0087 설명 자료(11/27). 무엇이 있고, 무엇이 빠졌고, 무엇을 골라야 하는지. 고른 뒤 ADR로 남깁니다. "가설"이라고 적은 것은 아직 확인 안 한 것입니다.

1. 두 낱말부터

로깅 = 일기장

일이 생길 때마다 한 줄씩 적어 둠. 나중에 "그때 무슨 일이 있었지?"를 찾아봄.

{"rid":"req_efb8…","path":"/v1/runs/{runId}/verification/photo",
 "status":200,"ms":4767.7,"db_ms":6.7}
우리 서버는 이미 이렇게 남김(계획 0070)

모니터링 = 계기판

숫자를 15초마다 재서 그래프로 보고, 기준을 넘으면 알람. "지금 괜찮나?", "한 달 동안 어떻게 변했나?"

초당 요청 수응답 시간오류율CPU·연결 풀

구글 SRE 책의 "골든 시그널" 네 가지: 트래픽·지연·오류·포화도

여기에 하나 더: 오류 수집

예외나 크래시가 나면 그 순간 상황(어느 코드 줄, 기기, 앱 버전, 요청 ID)을 자동으로 보내고, 같은 오류끼리 묶어 몇 명이 겪었는지 보여 줌. 로그를 뒤지지 않아도 "새 오류가 생겼다"를 먼저 알려 줌.

2. 지금 우리 상태

항목상태내용
서버 요청 로그있음요청마다 JSON 한 줄(경로는 라우트 틀이라 ID 안 남음), OCR 장별 시간. journald에 저장, journalctl로 봄
요청 ID있음응답 머리 X-Request-Id, 껍데기 meta.requestId
로그 보관 상한없음journald 1.6 GB 사용 중, 상한 설정 안 함
서버 오류 수집없음500이 나도 아무도 모름
지표·대시보드없음숫자는 k6 부하 테스트 때만 손으로 잼
알람없음서버가 죽어도, 매일 백업이 실패해도 모름
앱 크래시 수집없음출시 빌드는 오류를 어디에도 안 보냄(개발 빌드만 폰 안 파일)
제품 지표 이벤트자리만POST /v1/events가 204만 돌려줌(저장 안 함)

오라클 서버 여유(11/27): ARM 2코어, 메모리 11 GB 중 약 1.5 GB 사용, 디스크 96 GB 중 20 GB 사용 → 수집 도구를 같이 띄울 자리는 있음(CPU 부담은 재 봐야 함)

3. 다 갖추면 이렇게 흐릅니다 (추천안)

파랑 = 오라클에 우리가 띄우는 수집·저장, 초록 = 보는 곳, 주황 = 서버 바깥 서비스. 서버가 통째로 죽으면 Grafana도 같이 죽으니 UptimeRobot이 바깥에서 알려 줘야 함.

정할 것 5 · 범위와 순서

  1. 빨리 효과 큰 것: 서버 Sentry(요청 ID 태그) · UptimeRobot · 알림 채널 · journald 상한 · 매일 백업 실패 알림
  2. 지표·대시보드: /metrics(API별 요청 수·응답 시간·오류, 연결 풀·번호표 대기, OCR 시간·READ 비율, 실시간 접속 수) + Prometheus + Grafana 골든 시그널 대시보드
  3. 로그 모으기: journald → Alloy → Loki, Grafana에서 요청 ID로 검색, 로그 레벨 정리, 토큰·개인정보가 안 찍히는지 점검
  4. 앱 크래시: Sentry Unity SDK, 맥에서 dSYM 올리기, 앱 오류에 서버 요청 ID, 개인정보처리방침(상준)

제품 지표(/v1/events로 보정 완주율 등)는 이벤트 목록을 상준과 정해야 해서 따로 계획.

5. 조심할 것

  • 공개 저장소: DSN·비밀번호·웹훅 주소는 서버 .env에만
  • 개인정보: 로그·오류에 카카오 토큰·JWT·사진을 넣지 않음, 오류 수집의 "개인 정보 보내기" 끔. 바깥 서비스(Sentry)를 쓰면 개인정보처리방침에 적음
  • uvicorn 프로세스가 여럿(api 2개): 숫자를 프로세스마다 따로 세서 합쳐야 함(Prometheus 다중 프로세스 방식)
  • 서버 부담: 도입 전·후 k6로 같은 시나리오를 돌려 처리량이 떨어지지 않는지 → 이것 자체가 비포·애프터 기록
